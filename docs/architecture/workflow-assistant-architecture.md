# 第一部分：定位

## 1.1 一句话定位

Workflow 是一个**持有责任、主动发起、在你所有触达点上出现的智能助理**。

- 不是中转层，不是任务队列，不是群聊总结工具。
- 是**第二个我**：替你盯着你托付的事，在需要时找到你，经你授权后落到正确的机器上执行。
- 大脑（判断与授权）在 Workflow；触手（执行）在 Agent Runtime；触达点（你在哪）在设备与渠道。

判断标准：**任何功能如果不能回答"它在替用户承担什么责任"，就不属于本方案。**

## 1.2 与同类产品的分界

| | WorkBuddy | ZCode / Codex | AgentDock | Workflow |
| --- | --- | --- | --- | --- |
| 发起方向 | 部分主动 | 完全被动 | 被动 | **主动** |
| 核心对象 | 会话 / 记忆 | 会话 | 工具调用 | **责任（Commitment）** |
| 判断位置 | 平台 | 客户端 | 无判断 | **你自己的服务器** |
| 执行位置 | 平台侧 | 本机 | 多机（工具层） | **确定的归属节点** |
| 状态同步 | 记忆/配置 | 无 | 无 | **事件溯源 + 签名 + 中继** |
| 能否问执行器"做完了吗" | 否 | 否 | 否 | **是（Probe）** |
| 能否自我优化 | 平台内部 | 否 | 否 | **是（体检闭环）** |
| 记忆归属 | 平台账号 | 本地会话 | 无 | **你自己的 git 仓库** |

没有任何**单一机制**是独一份的。独一份的是组合：判断循环跑在你自己的服务器上、记忆是你自己可读可改的文件、执行落在你的机器上、能向执行器探询经验证的真实状态、并且能基于反馈改进自己的行为。

**如果这个组合对你没有实际价值，那就应该停。** 这是本方案唯一的正当性来源。

## 1.3 三个循环

| | 判断循环（大脑） | 记忆维护循环（大脑） | 执行循环（触手） |
| --- | --- | --- | --- |
| 位置 | Workflow Server | Workflow Server | 执行节点上的 Agent Runtime |
| 触发 | 新信号、责任状态变化、定时评估 | 定时 / 每批信号后 | 已授权的 Task，或一次 Probe |
| 形态 | 单次 LLM 调用，**无工具** | **有界**读写循环（读信号、写记忆文件） | 完整 agent loop |
| 输入 | 固定几个记忆文件 + 信号 | 新信号与事件 | 一个明确的目标 |
| 输出 | Proposal | 更新后的记忆文件 + git commit | 结果 + 证据 |
| 模型 | 便宜、快、可高频 | 便宜 | 强、慢、贵 |
| 能否打扰用户 | 能，这是它的职责 | 否 | **不能** |

关键区分：

- **判断循环不是 agent loop**：它不探索、不调工具，只读 keeper 维护好的固定文件。这保证判断便宜、快、可复现。
- **记忆维护是有界的**：只能写记忆仓库，不能碰项目代码，有 token 与时间预算，失败不阻塞判断。
- **执行器从不决定打扰用户**，只回话给大脑。

**物理上先不要拆服务。** 第一阶段三者同进程，只在模块边界上分开。

# 第二部分：架构

## 2.1 分层

```
┌───────────────────────────────────────────────────────┐
│ 触达点  Touchpoints                                    │
│ 飞书（手机+桌面）/ Web 控制台 / 桌面客户端 / 语音       │
├───────────────────────────────────────────────────────┤
│ 渠道适配  Channel Adapters                             │
│ 飞书群 / 飞书私聊 / 未来其他渠道                        │
├───────────────────────────────────────────────────────┤
│ 大脑  Brain（Workflow Server）                         │
│  信号摄入 → 责任模型 → 记忆维护 → 判断 → 提案           │
│  → 授权 → 回复策略 → 反馈回流                           │
├───────────────────────────────────────────────────────┤
│ 权威  Authority（Workflow Core）                       │
│  任务模型 / 项目注册表 / 执行归属 / 策略快照 / 审计     │
│  对等同步 / 事件日志 / 幂等                             │
├───────────────────────────────────────────────────────┤
│ 执行  Execution                                        │
│  Agent Runtime（有 LLM，实现统一契约）                  │
│  Device Actuator（哑设备，无 LLM，后期）                │
└───────────────────────────────────────────────────────┘
```

规则：

- 上层可调用下层，下层不得反向调用。
- **大脑不得绕过权威层直接派活。** 所有执行都经过 Task 模型与 executor 归属校验。
- **执行层不得直接向用户或群里发消息。** 回复一律经大脑的回复策略。

## 2.2 概念模型

| 实体 | 含义 | 关键性质 |
| --- | --- | --- |
| Signal | 一次原始观察：群消息、语音、会话轮次、文件变更、定时触发 | 不可变、只追加 |
| Commitment | Workflow 替你承担的一项责任 | 有生命周期，被信号更新 |
| Memory | 记忆文件：偏好、项目现状、观察、渠道上下文 | 人可读可改、git 版本化 |
| Proposal | 一次需要你决策的请求 | 有选项、紧迫度、否决窗口 |
| Task | 一次已授权的执行 | 沿用 executor 归属与策略快照 |
| Probe | 一次只读的状态探询 | 不建任务、不占 lease、可回答"不确定" |
| Presence | 你此刻在哪 | 短生命周期，不长期落库 |
| Feedback | 你对助理行为的一次反馈 | 自我优化的唯一输入 |
| Capability Endpoint | 能做事的端点 | 分 Agent Runtime 与 Device Actuator |

关系：

```
Signal ──证据──> Commitment ──需要决策──> Proposal ──授权──> Task ──执行──> 结果
                     │                                        │
                     └──定期评估（无信号也触发）              └──Probe（只读，不建 Task）
                              ↑
                    记忆文件（keeper 维护，git 版本化）
                              ↑
                     Feedback ──> 自我优化闭环
```

两个容易混淆的边界：

- **Signal 不是触发器，是证据。** 信号进来只是更新责任模型；是否打扰用户由**责任自身的注意力策略**决定。因此"build 红了三天"可以在没有任何新信号时发生。
- **Task 不是 Commitment。** Commitment 是"我替你记着的责任"，Task 是"为履行它执行的一次动作"。一个 Commitment 可以产生零个、一个或多个 Task。

## 2.3 责任驱动：Commitment

### 为什么需要它

如果核心对象是"来自某个信号的提案"，系统就只在有事发生时才有反应，形状上等同任何一个主动弹窗的助手。真正的区别是：**Workflow 持有意图，并持续评估。**

### 字段

```
Commitment
├── commitment_id
├── owner_id
├── scope
│   ├── project_id          可空；空表示个人事务
│   └── channel_ref         来源渠道
├── statement               我替你承担什么（一句话）
├── state                   active | needs_decision | fulfilled | dropped | expired
├── trigger_policy          何时重新评估
├── attention_policy        何时该打扰你
├── due_at
├── source_signal_ids
├── evidence_refs
└── version
```

`trigger_policy`：`on_signal` | `every:<duration>` | `at:<timestamp>` | `on_state_change`
`attention_policy`：`immediate` | `daily_digest` | `threshold:<condition>`

### 存储

Commitment 是**权威数据**（需要状态机与审计），存数据库；但它的人类可读视图由 keeper 同步到 `projects/<id>/commitments.md`，方便你直接看和改。

### 生命周期

```
新建 ──> active ──┬──> needs_decision ──> (授权) ──> active / fulfilled
                  ├──> fulfilled
                  ├──> dropped
                  └──> expired
```

状态变化只通过追加事件产生。`needs_decision` 是唯一触发 Proposal 的状态。

### 例子

| 场景 | Commitment | trigger | attention |
| --- | --- | --- | --- |
| 群里有人问"那个功能好了没" | 向群里给出项目 A 该功能的状态 | on_signal | immediate |
| 保持主线绿 | 主线构建健康 | every:1d | threshold:红>3d |
| 答应给 X 的东西 | 交付给 X | on_signal | threshold:临近 due |
| 项目 Y 停滞 | 推进项目 Y | every:2d | threshold:停滞>5d |

后三条**不需要任何外部信号**就会产生提醒。

## 2.4 判断循环

每次 tick：

```
1. 取自上轮以来的新信号
2. 每个信号尝试挂到已有 Commitment；挂不上则新建（低置信度，不打扰）
3. 重新评估 trigger_policy 命中的 Commitment
4. 对 attention_policy 命中的，生成 Proposal
5. 按 紧迫度 × 置信度 排序，去重
6. 非紧急的合批为摘要；紧急的单发
7. 交给授权与回复策略
```

约束：

- **单次判断必须便宜。** 用最便宜的可用模型，只读固定几个记忆文件 + 相关信号片段。
- **判断不探索、不调工具。** 上下文不足时标记出来，交给 keeper 或一次有界检索，不在判断里迭代。
- **判断失败不得静默。** 解析失败、模型不可用、消解不确定都留可观察记录，下轮重试或降级。
- **不得产生副作用。** 只写 Commitment/Proposal，不写 Task，不发消息。
- **幂等。** 同一信号重复摄入不产生重复 Commitment。

## 2.5 执行循环

- 由**已授权的 Task**或**一次 Probe**触发。
- 运行在执行节点的 Agent Runtime 上，有完整工具面。
- 必须遵守执行权威校验：`executor_node_id` 与策略快照。
- 结果必须带证据（commit、版本、测试输出、文件引用），因为下游可能**公开发布到群里**。
- 执行器不得直接联系用户或群。

## 2.6 记忆与上下文：文件化 + 技能驱动

### 决策

**不建自建上下文装配层。** 记忆落地为文件，由一个受技能约束的 CLI 代理读写。

| | 自建装配层 | 文件 + CLI + 技能 |
| --- | --- | --- |
| 记忆形态 | 数据库表，改结构要迁移 | 文件，随时可加 |
| 人类可读可改 | 否 | **是** |
| 版本与回滚 | 需自建 | **git 天然支持** |
| 检索方式 | 关键词 / 结构化查询 | 语义 + 探索 |
| 新增记忆类型 | 建表 + 迁移 + 改代码 | **加个文件** |
| 维护成本 | 高 | 低 |

### 数据分家（关键）

**不是所有东西都该文件化。** 按用途分开：

| 类别 | 存哪 | 理由 |
| --- | --- | --- |
| 权威数据：任务、项目、事件、同步、幂等 | **数据库**（现有 `core-db`） | 需要事务、幂等键、跨节点事件溯源，文件做不到 |
| 记忆数据：偏好、项目现状、责任视图、观察、渠道上下文 | **文件** | 需要人可读可改、可版本化、schema 自由 |

这条分界很重要：**不要用文件做跨节点同步**，也不要把记忆塞进表里。

### 记忆仓库布局

```
<workflow-memory>/            git 仓库，可版本化
├── MEMORY.md                 索引：什么在哪里
├── profile/
│   ├── preferences.md        你的偏好（何时可打扰、哪些群可自动回复）
│   └── people.md             相关的人与关系
├── projects/<project-id>/
│   ├── context.md            项目现状
│   ├── commitments.md        责任的人类可读视图
│   └── notes/                观察与决策记录
├── channels/<channel-id>/
│   └── recent.md             近期上下文（由 keeper 按 TTL 清理）
└── journal/
    └── YYYY-MM.md            追加式观察日志
```

### Workflow 记忆技能

一个 skill（`workflow-memory`）规范 CLI 的读写行为：

- **何时读哪个文件**：判断项目状态读 `projects/<id>/context.md` + `commitments.md`；判断是否该打扰读 `profile/preferences.md`
- **怎么写**：只追加，不覆盖；每条记录带时间戳与来源
- **禁止写什么**：凭据、token、本机绝对路径、环境变量值（沿用安全红线）
- **命名与结构约定**：固定字段，便于后续解析
- **清理规则**：`channels/*/recent.md` 由 keeper 按 TTL 裁剪

**技能是行为规范的唯一来源**：改技能就改行为，不用改代码。这也是为什么这套做法比自建装配层省事。

### 记忆维护循环（有界）

```
每 N 分钟 / 每批信号后：
  1. 读取新信号与事件
  2. 按技能约定更新记忆文件（追加观察、更新项目现状与责任视图）
  3. 按 TTL 清理渠道上下文
  4. 必要时合并 / 压缩过长的文件
  5. git commit（留下可回滚的历史）
```

约束：

- 单次运行有 token 与时间预算。
- **只能写记忆仓库**，不能碰项目代码、不能发消息。
- 失败不阻塞判断（判断用上一版记忆继续跑）。

### 判断调用怎么拿上下文

判断调用**不自己探索**，只读 keeper 维护好的固定几个文件——便宜、快、可复现。只有当判断显式标记"上下文不足"时，才允许**最多一次有界检索**。

### 审计

**不再需要 `context_snapshot` 表。** 改为记录 keeper 与判断调用的**读写日志**：读了哪些文件、写了哪些文件、git commit hash。要复盘某次判断，checkout 对应 commit 即可——**比预计算快照更可靠，也更便宜**。

### 边界与风险

| 风险 | 缓解 |
| --- | --- |
| 记忆文件膨胀 | keeper 定期压缩；单文件大小上限 |
| 记忆漂移（写错） | 只追加 + git 历史可回滚 + 你可以直接改文件 |
| keeper 越权 | 只能写记忆仓库，工作目录隔离，凭据不落盘 |
| 判断读不到关键信息 | 显式标记"上下文不足"，触发一次有界检索 |

### LLM 落点

`packages/core/src/ai/server-llm.js` 已提供 `ServerLlm`：支持直连 API（`baseUrl + apiKey + model`）或 CLI 子进程两种模式。**这就是"Workflow 自带 LLM"的实现，不需要 DSH。** 建议把 `index.js` 里硬编码的 DSH 路径改为可配置，或直接走直连 API。

# 第三部分：协议契约

## 3.1 渠道适配

已有基础：`workflow-core/packages/core/src/feishu/{service,client}.js`，飞书长连接、卡片推送、`message → task` 管线，测试见 `test/feishu-service.test.mjs`。

新增要求：

- **入站分类**：区分"提到我"、"回复我"、"群里与我相关"、"直接私聊"四类，给不同优先级。
- **出站过滤**：回复必须经回复策略（3.4）与**受众过滤**（第七部分）。
- **可识别性**：机器人在群里必须可见地表明助理身份（可配置），不伪装成用户本人。
- **每渠道可独立开关**，并有全局 kill switch。

## 3.2 Probe 状态探询（本方案核心新增协议）

场景：群里有人问"你那个 xxxx 做好了没"。Workflow 需要向项目 A 的执行器**问一句状态**，而不是派新任务。

现有 Bridge 协议（`packages/core/src/bridge/service.js`）只有执行类动词：`pull` / `heartbeat` / `events` / `interactions` / `result` / `release`。必须新增只读探询。

### 契约

```
POST /api/v1/probe
Auth: peer token 或内部调用
Body:
{
  "probe_id":   "稳定幂等键",
  "project_id": "proj-a",
  "question":   "登录功能完成了吗",
  "refs":       [{ "type": "commit|issue|file|version", "value": "..." }],
  "budget_ms":  60000,
  "evidence_required": true
}

立即返回:
202 { "probe_id": "...", "state": "accepted" }

完成后（轮询或推送）:
{
  "probe_id": "...",
  "state": "answered",
  "verdict": "done | not_done | unknown",
  "confidence": 0.0-1.0,
  "evidence": [{ "kind": "...", "ref": "...", "observed_at": "..." }],
  "suggested_reply": "...",
  "cost_ms": 12345
}
```

### 硬约束

| 约束 | 理由 |
| --- | --- |
| 不创建 Task、不占 lease、不计 attempt | 群里随口一问不该污染任务队列 |
| 只读、无副作用 | 不得 commit、改文件、发消息 |
| 异步 + 有超时 | "经过一番努力"可能几分钟，不能阻塞渠道 |
| `unknown` 是一等结果 | 错误宣称"完成"比"不确定"危害大得多 |
| 必须带证据 | 结论会公开出现在群里 |
| 按 `probe_id` 幂等 | 网络重试不得重复调查 |
| 按项目限流 | 防止被群消息打爆执行器 |

### 与 Task 的边界

Probe 是"读"，Task 是"写"。Probe 发现"没完成"之后是否升级为 Task，**由大脑决定，不由执行器决定**。

## 3.3 引用消解

问题："你那个 xxxx 做好了没"里没有任何稳定标识。

需要：

1. **项目语义字段**：`aliases[]`、`description`、`keywords[]`，落在记忆仓库 `projects/<id>/context.md` 与项目注册表里。
2. **渠道短期上下文**：`channels/<id>/recent.md`（TTL 由 keeper 管理）。
3. **一次消解调用**：输入 `(当前消息, 别名, 近期上下文, 活跃 Commitment)`，输出 `(project_id?, commitment_id?, confidence)`。

硬规则：

- 高置信度 → 直接 Probe。
- 中置信度 → **回问**，且在私聊或低可见度渠道问，不要在工作群里问。
- 低置信度 → 记为低置信度 Commitment，不打扰。

**消解失败必须可见。** 最坏的结果不是"我不确定"，而是自信地映射到错误项目、然后拿错误项目的事实去公开回复。所有消解结果（含置信度）留档作为反馈。

## 3.4 授权与回复策略

### 三层回复

| 层级 | 内容 | 自主性 | 前提 |
| --- | --- | --- | --- |
| T1 | 来自 Probe 的、有证据的事实性状态 | 可自主 | 证据完整 |
| T2 | 已确实记账的状态（"还没好，已进入排期"） | 可自主 | Task 或 Commitment 真实存在 |
| T3 | 工期估计、承诺、对人的评价、任何模糊情况 | **绝不自主** | 一律升级给用户 |

### 否决窗口

```
生成草稿 → 推送到当前在场触达点 → 挂起 N 秒（默认 30s）
  ├── 用户否决 → 丢弃，记录（同时是自我优化的负样本）
  └── 超时 → 发出
```

理由：在工作会议群替用户说错话，社交成本难以撤回，而系统还没有纠正机制。跑稳后再考虑把 T1 改为完全自动。

### 审计

每条自主回复记录：用了哪一层策略、依据哪些证据、是否被否决、最终文本。**没有审计记录，自主回复不可上线。**

### 升级路径

T3 与中置信度消解一律走**私聊**，不进群。用户在私聊决策后，再由大脑决定是否回群。

### 复用点

`packages/core/src/ai/suggestions-repository.js` 已经实现"AI 提案（pending）→ 人工批准（approved/rejected）"的闸门，并带 metrics 闭环。Proposal 直接扩展它，不要另起一套。

## 3.5 在场感知与通知

### 原则

**客户端上报事实，服务端广播，客户端本地决定响度。** 服务端不推导"你在哪"。

### 流程

```
服务端：把 Proposal/通知广播给所有在线触达点
每个触达点本地判断：
  idle < 60s   → 大声（系统通知 + 提示音）
  idle > 5min  → 安静（角标）
第一个展示的触达点回 ACK → 服务端通知其余触达点抑制
```

### 可用信号

| 信号 | 来源 |
| --- | --- |
| 系统空闲时长 | Electron `powerMonitor.getSystemIdleTime()` / `getSystemIdleState()` |
| 锁屏 / 解锁 / 休眠 | `powerMonitor` 事件 |
| 页面可见性与焦点 | 浏览器 `document.visibilityState` / `hasFocus()` |
| 当前活跃项目 | 客户端上报（不含内容） |
| 前台窗口 | Windows `GetForegroundWindow`（需原生模块，暂不做） |

### 隐私边界

- 空闲时长只上报**粗粒度分桶**，不报精确序列。
- 绝不采集窗口标题、按键内容、屏幕内容。
- 在场状态是**短生命周期**，不长期落库。
- 用户可一键关闭上报。
- 手机是**尽力而为**：后台不能心跳，靠网页开启或推送回执推断。

### 早期替代

**飞书本身就覆盖了"任何地方找到我"**（手机 + 桌面）。阶段 1 用飞书私聊做否决窗口，桌面客户端可以后置。

# 第五部分：自我优化（核心，不可省）

## 5.1 为什么它是核心

主动型助理的质量由两个错误率决定：

- **误报**：不该打扰时打扰你
- **漏报**：该提醒时没提醒

这两个率不靠人工调参，靠系统从反馈里学。**没有自我优化，Workflow 就是一个永远不变的规则引擎**，而不是一个会越来越懂你的助理。这是"贾维斯"和"一个会弹窗的脚本"的分界线。

## 5.2 已有基础（必须保留，不许丢）

`packages/core/src/index.js` 里已经有一套完整闭环，本方案**以它为起点，不重写**：

- `systemCheckupMetrics({taskRepository, workersRegistry, suggestionsRepository, knowledgeRepository, peerSyncService})` 采集系统指标（任务计数、失败任务、Worker 状态、待处理建议、知识量、同步健康）。
- `POST /api/v1/ai/checkup` 触发体检。
- 提示词要求模型"找出 workflow 不智能的地方，提出可执行改进"，输出 `skill | knowledge | settings | rule` 四类。
- 经 `ai_suggestions` 走"AI 提案 → 人工采纳/忽略 → 平台应用"（`applySuggestion`）。
- **反馈回喂已实现**：已采纳的作为正样本、已忽略的不得重复提案，并可用 `appliedAs` 查看批准实际改了什么。
- 管理台有"立即体检"入口。

**AI 永不直接改自己**——所有改动必须经人工批准，这是这套机制的安全基石，新设计不得放松。

## 5.3 新设计要扩展什么

### 1. 反馈信号（新增）

原来只有"采纳/忽略建议"这一种反馈。新设计要把**用户对助理行为的反应**也变成反馈：

| 反馈 | 信号 |
| --- | --- |
| 否决一条回复 | 负 |
| 忽略一条通知 | 负 |
| 丢弃一个 Commitment | 负 |
| 立即执行提案 | 正 |
| 显式纠正（"不对，我指的是…"） | 强信号 |

### 2. 指标（新增）

在系统指标之外，增加**助理行为质量**指标：

- 提案准确率 = 被采纳 / 总提案
- 通知误报率 = 被忽略 / 总通知
- 消解准确率 = 正确消解 / 总消解
- 回复否决率 = 被否决 / 总自主回复
- 响应时效 = 从责任成立到提醒的延迟

### 3. 调整对象（新增）

除原有的 `skill | knowledge | settings | rule`，扩展出可调项：

- 注意力阈值（何时该打扰）
- 置信度阈值（消解与回复）
- 回复策略分层边界
- 判断与消解的提示词
- **记忆技能**（`workflow-memory` 的读写约定）

### 4. 闸门不变

任何自我改动仍然：**提案 → 人工批准 → 应用 → 记录 → 回喂**。AI 永不直接改自己。

## 5.4 审计与回滚

每次自我改动记录：依据的指标、提案内容、批准人、应用结果、**应用后指标变化**。配置类改动留快照，记忆类改动靠 git 历史，两者都可回滚。

# 第六部分：Web 控制台

## 6.1 为什么需要它

飞书负责"找到你"，Web 控制台负责"让你看清和控制"：

- **飞书**是通知与快速决策通道：手机上点一下批准。
- **Web**是观察与管理通道：提案全貌、责任清单、记忆内容、执行历史、同步健康、体检建议。

两者不互相替代。你在手机上收到提案，在电脑上打开 Web 看完整证据和记忆。

## 6.2 页面结构

**助理视图（日常用）**

| 页面 | 内容 |
| --- | --- |
| 今日 | 待决策提案、活跃责任、最近通知与结果 |
| 提案 | 完整提案：要我决定什么、证据、选项、否决倒计时 |
| 责任 | 我替你盯着的事：状态、来源、下次评估、操作 |
| 对话 | 直接和 Workflow 交流（文本；语音后续） |
| 记忆 | 浏览记忆文件，可看、可改；带 git 历史与回滚 |

**运维视图（排查与配置）**

| 页面 | 内容 |
| --- | --- |
| 任务 | 执行状态、事件流、失败与重试 |
| 节点 | peer 注册、撤销、流游标 |
| 同步 | 同步全景、协议版本、签名与中继状态 |
| 体检 | 指标、AI 建议、采纳/忽略、应用效果 |
| 设置 | Worker、项目、凭据引用、渠道开关 |

## 6.3 视觉规范（"好看"是需求，不是装饰）

**主题**

- 深色为默认，提供浅色切换。服务器控制台场景，长时间看不刺眼。
- 用 CSS 自定义属性定义主题，切换只换变量。

**色彩**

- 一个主色 + 中性灰阶（8 级）+ 语义色四类（成功 / 警告 / 危险 / 信息）。
- **语义色只用于状态，不用于装饰。** 满屏彩色是廉价感的来源。
- 危险操作按钮才用危险色，且必须二次确认。

**字体与排版**

- 系统字体栈；ID、哈希、路径用等宽。
- 类型标尺 6 级（12 / 14 / 16 / 20 / 24 / 32）。
- 正文行高 1.6，标题 1.3。

**间距与形状**

- 4px 基准的间距标尺：4 / 8 / 12 / 16 / 24 / 32 / 48。
- 卡片圆角 8px，按钮与输入框 6px。
- 阴影克制，只用于浮层与下拉。

**图标**

- 内联 SVG 线性图标，24px 网格，1.5px 描边。
- **不用 emoji。**
- 图标集统一，不自造混搭。

**动效**

- 150–200ms，只在状态变化时触发。
- 不做装饰性动画。加载用骨架屏，不用转圈。

**状态可见**

- 任何异步操作都有 loading / 成功 / 失败三态。
- 失败给出可读原因和下一步动作，不弹裸错误码。

## 6.4 交互原则

- **提案卡片是核心。** 一屏之内要能回答：要我决定什么、依据是什么、有哪些选项。
- **否决倒计时可视化。** 剩余时间要看得见，不能悄悄过期。
- **危险操作二次确认。** 撤销节点、删除记忆、关闭渠道。
- **实时更新。** 提案、任务、同步状态用 SSE 推送，不靠手动刷新。
- **键盘可达。** 常用操作有快捷键，焦点顺序合理。

## 6.5 响应式

- **桌面**：左侧导航 + 内容区；宽屏可并排（列表 + 详情）。
- **手机**：底部导航 + 单列卡片。提案与否决要能单手完成。

## 6.6 技术选型

**建议：无构建步骤。**

- 原生 HTML / CSS / JS，由 Core 直接托管静态资源。
- 内联 SVG 图标，不引图标库。
- 数据走现有 HTTP API（复用现有认证）。
- 实时更新用 SSE（服务端单向推送），操作用 REST。

理由：清仓后仓库没有前端工具链，`admin/console.js` 已经证明这条路可行。引入 Vite + React 会重新带进 `node_modules` 与构建产物，而"好看"主要来自设计规范，不是框架。

**例外**：若后续交互复杂度显著上升（例如记忆编辑器、图可视化），再评估引入轻量框架（Preact 等），并单独评估构建产物如何管理。

## 6.7 与现有管理台的关系

现有 `packages/core/src/admin/console.js` 是 Core 管理台。新 Web 控制台**取代它**：把运维视图的页面并进来，保留现有 API 与权限，不并行维护两套界面。

## 6.8 桌面端：同一套 UI + 原生能力

### 决策

**桌面端不另做一套界面。** 它加载服务器托管的同一套控制台，再通过 preload 暴露浏览器拿不到的原生能力。

```
┌──────────────────────────────────────────┐
│ 同一套 HTML / CSS / JS（服务端托管）      │
├───────────────┬──────────────────────────┤
│ 浏览器        │ 桌面壳（Electron）        │
│ 页面可见性    │ + 系统空闲时长            │
│ 网页通知      │ + 系统原生通知            │
│ —             │ + 本地凭据存储            │
│ —             │ + 后台常驻 / 开机自启      │
└───────────────┴──────────────────────────┘
```

### 桌面壳独有的能力（浏览器做不到）

| 能力 | 为什么必须桌面端 |
| --- | --- |
| 系统空闲时长（`powerMonitor`） | 3.5 的响度判断依赖它；浏览器只有页面可见性 |
| 锁屏 / 解锁 / 休眠事件 | 判断"人是否在这台机器前" |
| 系统原生通知 | 网页通知要求标签页开着，桌面端可后台常驻 |
| 本地凭据存储 | 执行器凭据绝不能进浏览器 |
| 后台常驻 + 开机自启 | 主动型助理必须一直在跑，否则"找到你"不成立 |

**结论：桌面端不是"网页的打包"，它是让主动感知成立的载体。**

### 连接方式

- **瘦客户端**：加载服务器托管的控制台，连服务器 API。默认形态。
- **节点身份**：同一个桌面端可把自己注册为执行节点（本机 Agent Runtime 接入），凭据只存本地。
- **不做版本耦合**：界面从服务器加载，保证 UI 与 API 同版本，避免客户端版本漂移。
- **本地模式（后续）**：若需要离线 / 单机使用，再评估在桌面端内嵌本地 Core；不进第一阶段。

### 技术形态

Electron（`powerMonitor` 与原生通知都是现成能力）。preload 只暴露必要接口，最小权限；renderer 不拿特权。

# 第七部分：安全与隐私

沿用现有红线，并新增本方案特有的约束：

1. 凭据、token、本机绝对路径、环境变量值**不得**进入信号、提案、回复、日志、记忆文件或知识库。
2. `credential` / `file_select` 只在 Worker 本地受控页处理。
3. **受众过滤（新增）**：同一事实在不同渠道的可披露程度不同。Probe 结果、项目名、内部状态在私聊可见，未必可在工作群发布。回复前必须按渠道受众过滤，宁可模糊，不可泄漏。
4. **无证据不得自主发布事实（新增）**：自主回复必须有可审计的证据链。
5. **keeper 的写入边界（新增）**：记忆维护只能写 `<workflow-memory>/`，不能写项目代码，不能发消息，不能读凭据。
6. **Web 控制台的权限（新增）**：沿用现有认证与角色；记忆编辑、凭据引用、节点撤销等敏感操作需要二次确认并留审计。

7. [x] **最小 Web 控制台**：Core 在 `/console` 托管，无构建步骤、**无外部 CDN 依赖**（原生 DOM 代码 + 设计令牌，所有服务端值显式转义）。登录、待决策列表、完整证据链、草稿、否决倒计时、批准/否决/发送。会话失效自动回到登录页。已部署。

**验收**：

- 群里问一句项目状态，系统在无人工干预下产出**带证据**的草稿。
- 草稿在否决窗口内可被撤回；超时后发出。
- 否决与超时两条路径都有审计记录和反馈记录。
- Probe 不产生任何 Task、不占用 lease。
- Web 控制台能独立完成一次否决，且手机上单手可操作。

**这一阶段跑通之前，不要碰任何其他功能。**

## 阶段 2：责任模型与记忆

**目标**：无新信号也能主动提醒；记忆文件化并自动维护。

工作项：

1. [x] **Commitment 存储**：`commitments` + 追加式 `commitment_events`（状态是事件日志的投影，不是覆盖写）；`trigger_policy` 与 `attention_policy` **两个独立时钟**，周期触发在自身周期内不重复打扰；`dueForAttention()` 无副作用，只报告不动作。7 个测试覆盖策略语法、阈值语义与去噪。
2. [x] **记忆仓库**：`memory/store.js` 提供布局初始化、原子写、追加、git 提交、历史与按版本读取；**所有路径限定在仓库内**，逃逸路径直接拒绝。Core 每次启动都会建好布局。
3. [x] **`workflow-memory` 技能**：`workflow-core/skills/workflow-memory/SKILL.md`，规定读哪个文件、只追加不覆盖、禁止写入的内容（凭据/绝对路径/环境变量/原始消息全文）与输出格式。
4. [x] **记忆维护循环（keeper）**：有界运行——固定大小的摘要输入、只应用 `append`/`write`、单次写入上限、逃逸路径丢弃并记录、失败不阻塞（下一轮用上一版记忆）。**默认关闭**（`WFC_MEMORY_KEEPER_ENABLED`），因为每次运行都调用模型。
5. [x] **判断循环**：`judgment/loop.js`。到期责任交给模型判断"现在还值不值得打扰"，值得的才变成提案（**T3、无渠道目标**——提醒是问用户的问题，不是助手能自己发的回复）。没有到期项时**完全不调用模型**；模型不可用时**不消费本轮**，责任保留待重试；看过的一律标记已评估，避免下一轮重复唠叨。`at:` 触发改为一次性。已部署。
6. [x] **信号挂载**：`signals/` 记录每条入站消息（按 `(channel, source_ref)` 去重）。**只有指向用户的消息**（mention / reply / direct）才可能挂载或开启责任；群里的普通发言只更新记录。恰好一条匹配时挂载并刷新活动时间（这正是 `stale` 阈值读取的字段）；多条匹配时**不猜**；无匹配则开一条**安静的责任**（`待确认：` 前缀 + `daily_digest`，只进摘要不打扰）。记录失败不影响原有消息链路。已部署。
7. [x] **摘要合批**：`digest/service.js`。只有 `daily_digest` 策略的责任进摘要，紧急的**绝不稀释**进摘要；一条只出现一次（是通知不是唠叨）；汇总成**一条低紧迫度 T3 提案**（无渠道目标）。没有可汇总的内容时不产出空卡片。已部署。
8. [x] **Web 记忆浏览**：`GET /api/v1/memory/tree|file|history`、`POST /api/v1/memory/revert`（全部 admin）。路径逃逸被拒绝而不是被读取；**回滚本身也是一次提交**，历史保持线性可逆。控制台新增"记忆"页：文件树 + 文件内容 + 历史（带回滚按钮）。已部署。

**验收**：

- 在**没有任何新信号**的情况下，系统能因责任到期或停滞主动提醒（例：build 红三天）。
- 同一信号重复摄入不产生重复 Commitment。
- 记忆仓库每次 keeper 运行都有 git commit；可从历史回滚任意一版记忆。
- keeper 无法写入记忆仓库之外的任何路径。
- 判断调用失败可观察、可重试，不静默。
- Web 端能看清"Workflow 现在认为什么"，并能回滚错误记忆。

## 阶段 3：引用消解

**目标**：模糊引用能正确消解或回问，绝不猜错。

工作项：

1. [x] **项目语义字段**：存在现有 `metadata` 里（`aliases[]`、`keywords[]`、`description`），**不动同步 schema**；可通过 `PATCH /api/v1/workflow/projects/:id` 设置。
2. [x] **渠道短期上下文**：`signals/channel-context.js` 把渠道近期观察写进 `channels/<id>/recent.md`，**双重有界**（3 天 + 行数上限）；chat 引用会被净化为安全文件名，无法逃逸仓库。消解路由在给了 `channel_ref` 时自动读取该上下文。已部署。
3. [x] **三级置信度**：`resolve/` 先做**字面归一化匹配**（单个命中直接 high，不调用模型）；多个命中交给模型，按置信度分档：high 行动 / medium 私聊回问 / low 不打扰。**模型点名了不在候选里的项目直接丢弃**；无法解析或空回答一律降为 low，绝不猜。已部署。
4. [x] **消解留档**：每次消解（含拒绝决策的）都写入 `feedback`（`subject_type=resolution`，`source=tier`，明细含置信度与原因），供自我优化调参。已部署。

**验收**：

- "你那个 xxxx 做好了没"能映射到正确项目，或明确回问。
- 消解不确定时不调用 Probe、不回复群里。
- 消解记录可用于后续调优。

## 阶段 4：执行触达

**目标**：多端在场感知与通知。

工作项：

1. [x] **桌面壳**（Electron）：`workflow-shell/` 加载服务器托管的同一套控制台，**不另做界面**；preload 只暴露四项能力（`idleBucket` / `notify` / `serverUrl` / `platform`），沙箱 + 隔离，外链走系统浏览器。空闲状态来自 `powerMonitor`（操作系统实测，不是页面焦点）。**已端到端验证**：窗口渲染登录页，登录后上报 `kind=desktop` + OS 空闲桶。
2. [x] **在场广播**：`presence/` 由触达点上报事实（`idle_bucket` + 活跃项目），服务端**推导**而非猜测；报告带 TTL，崩溃的客户端会自然过期；`active()` 取最响的桶、同桶按最近上报；通知用**确认制**——首个 ack 生效，后来的抢不走，其余触达点据此静默。已部署。
3. [x] **本地执行器接入**：桌面壳监管本机 Worker 进程（不自己执行）——凭据用**操作系统凭据存储**封存，不经 preload 桥、不落可读文件；环境变量优先，重新配置不会悄悄沿用旧令牌；**执行器用真实 Node 而非 `process.execPath`**（Electron 内置 Node 无 `node:sqlite`）；有令牌即自动启动，崩溃重启上限 3 次。**已端到端验证**：壳封存令牌 → 拉起 Worker → 注册到 Core（`workers_online=1`）。
4. [x] **Web 在场卡片**：控制台在加载、可见性/焦点变化、以及每 30 秒上报自己的空闲状态。已部署。

**验收**：

- 通知只在在场设备大声，其他设备安静。
- **桌面端与浏览器共用同一套界面代码，不存在两套 UI。**
- 桌面端与浏览器都不向服务端上报任何窗口标题或内容。
- 本地凭据不出本机。
- 桌面端关闭后，系统仍能通过飞书找到你（不依赖桌面端在线）。

## 阶段 5：策略完整化

**目标**：授权与回复策略完整、可审计、可关闭。

工作项：

1. [x] **T1/T2/T3 完整分层**：每层在**创建时**就要为真——T1 必须带证据、T2 必须引用它所说的那条记录；tier 成为系统会校验的断言，而不是调用方随手填的标签。
2. [x] **受众过滤**：按渠道受众过滤——群消息额外隐藏内部标识（任务/提案 ID、UUID），因为**结构本身就是信息**。
3. [x] **kill switch**：全局或按渠道目标关闭自主回复，存在 settings 里，**不用重新部署**即可生效；缺省即允许（全新安装不会默默拒绝说话）。
4. [x] **审计查询面**：`GET /api/v1/replies` 支持按渠道与 tier 过滤；控制台新增「回复记录」页，逐条显示内容、tier 和放行它的自主性来源。已部署。

**验收**：

- 无证据不得自主发布事实性陈述。
- 可按渠道关闭自主回复。
- 每条自主回复都能追溯到证据。

## 阶段 6：自我优化扩展

**目标**：把已有的体检闭环从"优化系统配置"扩展到"优化助理行为"。

工作项：

1. [x] **反馈采集**：批准（"问得对"）、否决（"太急了"）、责任丢弃（**最安静的负信号**——用户根本没看到通知，只是认定这件事不成立）全部写入 `feedback`；观察者抛错不阻塞状态变更。
2. [x] **助理行为指标**：并入体检——提案准确率/否决率、消解自动率、回复否决率、自主发送数、责任丢弃数。高否决率意味着打扰太急，低自动率意味着看不懂直白引用。
3. [x] **可调项扩展**：体检提示词现在点名可调的行为键（`assistant.attention`、`assistant.confidence`），让建议能直接瞄准注意力与置信度阈值。
4. [x] **应用与回滚**：每次应用建议都记录**替换前的值、设置后的值、以及当时的助理指标**；`GET /api/v1/ai/applications` 返回每项改动的**指标 delta**（且知道哪个方向是"变好"：否决率下降是改善，其余上升是改善）；`POST .../:id/revert` 恢复快照，重复回滚被拒绝。记忆仍靠 git 回滚。已部署。
5. [x] **Web 体检页**：指标卡 + 建议采纳/忽略；`GET /api/v1/ai/metrics` 暴露同一组数字。已部署。

**验收**：

- 体检能产出针对助理行为的改进建议，而不只是系统配置。
- 被忽略的建议不会重复提案（沿用现有机制）。
- 每次自我改动可追溯到指标依据，且可回滚。
- AI 无法在没有人工批准的情况下改动任何配置。
- Web 端能看出"这次改动让哪个指标变好了/变坏了"。

# 第十部分：风险与开放问题

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 自主回复出错 | 工作群社交成本高 | 三层策略 + 否决窗口 + 可关闭 |
| 消解猜错 | 拿错项目的事实公开回复 | 中置信度强制回问；消解留档 |
| 判断循环成本失控 | 高频调用贵模型 | 便宜模型 + 只读固定文件 + 摘要合批 |
| 记忆漂移或膨胀 | keeper 写错或文件无限增长 | 只追加 + git 可回滚 + 定期压缩 + 你可直接改 |
| keeper 越权 | 写到了不该写的地方 | 只能写记忆仓库；凭据不落盘 |
| 自我优化跑偏 | 优化目标与用户真实偏好偏离 | 人工批准闸门 + 指标变化可回滚 |
| Probe 被滥用 | 群消息打爆执行器 | 按项目限流 + 预算上限 |
| 执行器返回幻觉 | 无证据的"完成" | `evidence_required`，无证据降级为 `unknown` |
| Web 无构建方案后劲不足 | 交互变复杂后手写成本上升 | 先按 6.6 走，复杂度触发时再评估框架 |
| 范围再次膨胀 | 又去做图编排/多客户端 | 第九部分为硬边界 |

开放问题：

- 飞书之外的第二渠道选哪个？（取决于你实际用哪些群）
- Probe 的调查深度如何配置？（只读代码 vs 允许跑测试）
- 摘要的默认频率？（每日一次 vs 实时）
- keeper 的运行频率与预算？（太频繁浪费，太稀疏记忆滞后）
- 记忆仓库放哪台机器？是否需要跨节点同步（若需要，走 git 而非事件流）
- 自我优化的指标权重如何定？（误报与漏报哪个更不可接受）
- Web 控制台与飞书的分工边界？（哪些操作必须在 Web 完成，哪些飞书一键即可）
