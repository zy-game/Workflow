# 完成 Workflow JSONL Worker，并彻底删除 DSH

## 目标与边界

最终生产主链固定为：

```text
Feishu / HTTP API -> Workflow Core -> /worker -> Workflow JSONL backend
```

本轮执行以下 clean break：

- 全仓删除 DSH 生产代码、配置、数据库字段、测试夹具、部署脚本和文档，不保留兼容层或历史 `/dsh` 断言。
- `/worker` 保持唯一执行通道；不恢复 `/client`、REST claim、`transport: client` 或旧 approval protocol。
- OMP 不作为本轮工作内容：保留实验实现文件和显式 package export，但从 Worker 入口、环境配置、默认能力、部署与测试主链中移除。
- 完成可部署的 Workflow JSONL Worker，包括可靠投递、恢复、本地配置、安全凭据、loopback 管理 API/UI 和完整测试。
- 不迁移旧 schema；提升协议和数据库版本，旧版本明确拒绝启动。
- 不 commit、不 push，不修改无关的 `nul`、发布包或用户其他脏改动。

## 1. 删除 Core 与 Shared 中的全部 DSH

- 删除 `packages/core/src/models/dsh-sync.js` 和 `packages/shared/src/dsh-models.js`，移除 shared barrel export。
- 删除 `DshDriver`、中央模型 registry/probe 和 `ManagementAi` 的 DSH 装配；Core 启动不再读取 `WFC_DSH_UPSTREAM`、`WFC_MANAGEMENT_AI` 或连接 3081。
- Feishu 入口保留确定性的任务创建、上下文和 interaction 回复，不再经过 DSH triage。
- 删除 Core 管理 API/UI 中的模型、探测、AI decision 页面和 health 字段。
- 删除无生产消费者且依赖旧 `pending_approvals` 的 `ApprovalRegistry`；approval 统一保留为 `InteractionRepository` 的 backend-neutral interaction kind。
- 保留通用 transcript 规范化、secret redaction、证据过滤和知识去重；将完成后知识提取从 `ManagementAi` 拆成确定性的 completion hook，不保留 AI candidate vetting 或供应商事件假设。
- fresh Core schema 删除 `model_registry`、`model_registry_state`、`management_decisions` 等遗留表并提升 schema version；旧 schema 按现有策略明确报错，不做迁移。
- 将测试中的 `dsh.run`、DeepSeek plugin、fake DSH 和 `/dsh` tombstone 改为 backend-neutral fixture，或在对应功能删除后移除测试。

## 2. 固定 Workflow JSONL backend 契约

重构 `packages/worker/src/adapters/jsonl.js` 为完整 BackendContract 实现：

- 实现 `describe()`、`checkHealth()`、`start()`、`run()`、`resume()`、`inject()`、`cancel()`、`resolveInteraction()`、`dispose()`。
- 定义带协议版本和 request ID 的正式 JSONL 消息：`run`、`resume`、`inject`、`cancel`、`interaction_response`，以及 `session`、`event`、`progress`、`interaction_required`、`result`、`error`。
- `run` 与 `resume` 严格分离；resume 必须携带持久 `session_ref`，不得重放首次 prompt。
- 明确每会话进程生命周期和复用键；TaskRunner 传入稳定 task/conversation/session 上下文，不再出现 adapter 测试与生产调用不一致。
- 接入 `ProcessSupervisor`，统一追踪、取消、超时、关闭和 daemon disposal。
- 严格校验对象 shape、消息类型、request correlation 和 1 MiB 单帧限制；处理分块 stdout、残留 EOF 行、malformed/oversize JSON、未知消息、正常退出无 result、异常退出、stdin 背压及 error/exit 双触发。
- 正确定义 cancel/result 和 interaction response/result 竞态，保证一个 request 只产生一个 terminal outcome。
- child env 使用明确 allowlist/denylist，绝不包含 Core/Worker token、凭据或不属于所选 environment profile 的值。

## 3. 建立 Core ACK 与持久 outbox

当前 WebSocket `send()` 后立即删除 outbox 不构成可靠投递。本轮将协议升级并闭环确认机制：

- Shared 协议升级到 v4，新增 Core→Worker `ack`；所有需持久化的 Worker frame 均带稳定 `frame_id`。
- Core 新增按 `worker_id + frame_id` 唯一的接收记录，在同一事务中完成 frame 对任务/事件/interaction 的状态变更并记录处理结果，再发送 ack。
- 重复 frame 不重复追加事件或完成任务，而是返回同一 accepted/rejected ack；claim/ownership 错误也返回稳定结果。
- Worker 仅在收到 accepted 或确定性 rejected ack 后删除 outbox；断线、发送回调和超时均保留 frame，重连注册完成后按 sequence 串行重放。
- outbox 满时 Worker 进入 draining/error，拒绝新 dispatch；runner 不得因 `send()` 暂时失败删除 run。
- terminal frame 使用稳定 ID 持久化在 `completion_pending` run 中，ack 后才删除 run。

## 4. 完成 Worker 恢复和 interaction 状态机

- 修正 `TaskRunner` 构造，实际保存并使用 `projectRegistry`，并将 slot、run 和 outbox 生命周期拆清楚。
- 持久 phases：`dispatched`、`running`、`awaiting_input`、`completion_pending`；持久化 session ref、interaction ID、terminal frame ID、最后事件序号和必要的非敏感恢复元数据。
- `completion_pending` 重启只重放同一 terminal frame，不再启动 backend。
- `running` 仅在 backend 声明 resume 且存在 session ref 时恢复；缺失状态或 backend 不支持时 fail closed，并以稳定 terminal frame报告。
- `awaiting_input` 持久化 interaction ownership；Core 重投 response 后恢复 backend。credential/file_select 不进入 Core 明文 response。
- 对“Core 有 ownership、本地无 run”和“本地有 run、Core 已无 ownership”分别记录明确错误并隔离，不重放 prompt、不抢占任务。
- stop 流程先进入 draining、停止接收 dispatch、等待/分离任务、持久化状态并 dispose 子进程。
- 补齐 inject、cancel、detach、late completion 和重复 dispatch 的 claim-token/ownership 竞态处理。

## 5. Worker 本地配置、项目、环境和凭据

- 在 state dir 建立带 revision 的原子 `config.json`，作为 projects、backends、environment profiles 和 local admin 设置的权威来源；环境变量只负责 Core bootstrap、state dir 和可选首次 JSONL backend bootstrap。
- `ProjectRegistry` 改为只接受已存在目录，使用 `realpath`/Windows native canonicalization，不创建目录；拒绝相同、祖先/子目录、symlink/junction overlap 和未注册 workspace。
- backend 配置保存 command、args、enabled、capabilities、project policy 和 environment profile 引用，不保存 secret。
- `EnvironmentStore` 使用明确 schema、revision 和敏感 key 拒绝规则；`TOKEN`、`SECRET`、`PASSWORD`、`KEY`、`CREDENTIAL` 类值不能进入普通 profile。
- 新增 `CredentialStore` provider 接口：Windows 使用当前机器/账户作用域 DPAPI；Linux 使用受权限约束的外部/systemd credential reference。API 和日志只返回 metadata，不返回 secret；secret 仅在受控调用点临时解析，且默认不注入 JSONL child。
- credential 和 file_select 只允许 Worker loopback 管理面回答；Core/飞书只能看到待本地处理状态及非敏感结果引用。

## 6. Worker loopback 管理 API 与 Web UI

新增独立 `LocalAdminServer`，强制仅绑定 `127.0.0.1` 或 `::1`：

- 启动生成 state-dir session token；mutation 同时要求 session token、同源 Origin 校验和 CSRF header。
- API 覆盖：Worker/Core 状态、drain/resume、项目 CRUD、backend CRUD/health、environment CRUD、credential set/test/delete、runs/events/cancel、pending interactions answer/cancel/expire。
- 拒绝非 loopback bind；响应进行统一 secret/path 安全审计，credential endpoint 永不回传明文。
- 使用仓库现有无构建静态页面模式实现实际可用 UI：总览、项目、Backends、环境、凭据、运行和交互视图；具备 loading/empty/error/disabled/confirmation 状态和轮询更新。
- Core admin 只保留中心调度视图；本机路径、环境值、凭据和 file picker 不进入 Core admin API。
