# 32 · 性能基线

给「数据量上来会不会卡」一个可复跑的数字。不测模型、不测网络，只测本机 SQLite 上的三件慢事。

```bash
node scripts/bench.mjs                 # 默认 2 万行 / 2 千条事实
node scripts/bench.mjs --rows 50000 --facts 5000
```

## 基线（2026-11-12，Windows / Node 24 / 本机 SSD）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| store 写入 20,000 行 | 31.6 s（约 1.6 ms/行） | 单条 insert 串行写；批量导入才需要优化 |
| `find` + `where` + `limit 20` | 7.5 ms | 下推成 SQL（`json_extract`） |
| `find` + `order` + `limit 20` | 10.0 ms | 同上 |
| `find()` 全表扫描 20,000 行 | 30.4 ms | 没有 where/limit 时退回 JS |
| `count(where)` | 9.6 ms | 下推 |
| 日程 tick 扫描 10,000 行 | 13.4 ms | tick 每秒一次，就是一次 `collection.find()` |
| 记忆召回（2,000 条事实） | 25.4 ms/次 | 神经元激活 + 扩散 + 打分 |

## 解读与动作

- **日程 tick**：1 万条 13 ms，每秒扫一次可以接受；**超过 2 万条**要按 `next_at` 建索引
  或把查询缩到「未来 24 小时」窗口（现在没有窗口，见 NEXT 技术债）。
- **记忆召回**：2 千条 25 ms；线上实际事实量在千级以内，暂时没有体感。
  夜间巩固会压缩同主题低置信事实，这也是把数量压住的机制。到 1 万条再评估向量或倒排。
- **store 写入**：1.6 ms/行的串行写只影响批量导入（例如迁移/回放），
  日常单条写入（消息、任务状态）无感；真要批量，用 `transaction` 包起来。

## 什么时候重跑

- 发布前改动了 store / schedule / memory 的查询路径；
- 数据量翻倍（每年或每万条）；
- 出现「页面打开变慢」「tick 告警堆积」这类症状时先跑一遍，再决定优化哪一段。
