# 32 · 性能基线

给「数据量上来会不会卡」一个可复跑的数字。不测模型、不测网络，只测本机 SQLite 上的三件慢事。

```bash
node scripts/bench.mjs                 # 默认 2 万行 / 2 千条事实
node scripts/bench.mjs --rows 50000 --facts 5000
```

## 基线（2026-11-12，Windows / Node 24 / 本机 SSD）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| store 写入 20,000 行 | 13.8 s（约 0.7 ms/行） | 单条 insert 串行写；两次运行差异来自磁盘缓存 |
| `find` + `where` + `limit 20` | 8.8 ms | 下推成 SQL（`json_extract`） |
| `find` + `order` + `limit 20` | 11.8 ms | 同上 |
| `find()` 全表扫描 20,000 行 | 29.2 ms | 没有 where/limit 时退回 JS |
| `count(where)` | 7.5 ms | 下推 |
| **会话最近 20 条（20,000 行消息）** | **0.17 ms** | 走 `(session_id, created_at)` 索引；旧实现全表扫 29 ms |
| 日程 tick 全表扫 10,000 行（旧） | 12.2 ms | 改造前的每 tick 开销 |
| **日程 tick 窗口 20,000 行（新）** | **0.56 ms** | `ORDER BY next_at LIMIT 500`，按 `next_at` 索引 |
| 记忆召回（2,000 条事实） | 23.3 ms/次 | 神经元激活 + 扩散 + 打分 |

## 解读与动作

- **日程 tick**：已改成 `next_at` 索引 + 每批 500 条（2026-11-12）；2 万行 0.56 ms。
  同时到期超过 500 条会分多个 tick 处理并打 warn，不再一次性全表加载。
- **会话历史**：`recent()` 改成按 `(session_id, created_at)` 索引各取最近 N 条再合并，
  2 万行 0.17 ms；聊天记录再长，每轮对话也不再扫全表。
- **记忆召回**：2 千条 23 ms；线上实际事实量在千级以内，暂时没有体感。
  夜间巩固会压缩同主题低置信事实，这也是把数量压住的机制。到 1 万条再评估向量或倒排。
- **store 写入**：0.7 ms/行的串行写只影响批量导入（例如迁移/回放），
  日常单条写入（消息、任务状态）无感；真要批量，用 `transaction` 包起来。

## 什么时候重跑

- 发布前改动了 store / schedule / memory 的查询路径；
- 数据量翻倍（每年或每万条）；
- 出现「页面打开变慢」「tick 告警堆积」这类症状时先跑一遍，再决定优化哪一段。
