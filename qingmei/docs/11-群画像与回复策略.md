# 11 · 群画像与回复策略

> 同一个青梅，在不同群里必须有不同的"分寸"。
> 工作群里该给进度，吹水群里给进度就是事故——而分寸不能靠模型临场判断。

## 1. 为什么需要"群画像"

群里说话有三个特殊性：

1. **听众变了**：私聊只有你，群里可能有同事、客户、家人。
2. **语境变了**：工作群问"进度"是正常需求，吹水群问同样的话就是越界。
3. **责任变了**：机器人说错话，丢的是你的脸，不是它的。

所以每个群需要一份**画像（profile）**：它是谁、属于哪类、能看什么、能说什么。
画像由你（owner）在网页后台设置，不由模型猜。

## 2. 实体

```ts
interface ConversationProfile {
  id: string
  channel: ChannelId                  // 'feishu' | 'qq'
  platformConversationId: string
  title: string
  kind: 'group' | 'dm' | 'thread'
  tags: string[]                      // 'work' | 'casual' | 'family' | 'client' | 'temp'
  trust: 'owner' | 'member' | 'stranger'
  status: 'pending' | 'configured' | 'muted' | 'blocked'
  /** 可选：对标签默认策略的局部覆盖 */
  overrides?: Partial<Policy>
  discoveredAt: Date
  lastActiveAt?: Date
}
```

一个群可以被多个标签，冲突时按**标签优先级**合并：`blocked > client > work > family > casual`。
合并规则是"取更严格的那一个"（deny 优先），不做"或"运算。

## 3. 发现流程

```text
① 机器人被拉进群
     ├─ 飞书：im.chat.member.bot.added_v1
     └─ QQ：group_increase / 群通知
② 创建 Conversation，status = pending，发一条「新群待配置」到 owner 的端
③ 后台「群管理」出现该群：名字、渠道、成员数、发现时间、最近消息量
④ owner 打标签（可多选）+ 可选覆盖
⑤ 立即生效（策略缓存失效重算），下次消息就按新画像走
```

未配置的群**只回一句固定话术**：

> 权限未配置

这句话由**确定性路径**直接发出——不调模型、不召回记忆、不给工具。原因有两层：
一是省钱省延迟，二是即使内嵌 harness 挂了或欠费，这句也必须能发出去。

同时：该群在后台标记 `pending`，给 owner 推一条「新群待配置」（同群每天最多一次），
你打上标签后立即恢复正常。

这条默认值很重要——它保证"忘了配"等于"更安全"，而不是"泄露"。

## 4. 标签体系与策略矩阵

### 4.1 固定标签

内置六类，策略预置、不可删改，只能被覆盖：

| 标签 | 记忆可见 | 可用工具 | 回复长度 | 主动消息 | 数据分级 |
| --- | --- | --- | --- | --- | --- |
| **工作群** | 项目域 + 本群历史 | 只读（进度/日程/查询） | 中（≤300 字） | 仅任务里程碑 | `private`（限项目相关） |
| **吹水群** | 仅 `public` | 无 | 短（≤100 字） | 禁止 | `public` |
| **家人群** | `audience=family` | 日程 / 提醒 | 短 | 允许（低频） | `private`（家庭） |
| **客户群** | 无内部记忆 | 无 | 正式、短 | 禁止 | `public` |
| **临时群** | 无 | 无 | 一句话 | 禁止 | `public` |
| **未配置** | 无 | 无 | 一句话 | 禁止 | `public` |

### 4.2 自定义标签：必须继承，且带备注

你可以加自己的标签（「甲方群」「健身群」「家长群」），规则两条：

```ts
interface ConversationTag {
  id: string
  label: string
  /** 内置标签的 id；自定义标签必须挂靠一个，保证策略有默认值 */
  base: 'work' | 'casual' | 'family' | 'client' | 'temp'
  /** 备注：给人看，也给青梅判断用 */
  note?: string
  /** 只允许"更严格"，不允许比 base 更宽松 */
  tighten?: Partial<Policy>
  builtin: boolean
}
```

1. **必须挂靠一个内置标签作基座。** 策略 = 基座 + `tighten`。这样任何自定义标签都有一份
   合法的默认策略，不会出现"未知标签 → 无策略 → 放行"的漏洞。
2. **备注是给模型理解用的自然语言**：「这个群是甲方，说话要正式，不要提内部排期」。
   备注进 prompt，但不改变硬边界——硬边界仍由基座策略决定。

覆盖只能是**收紧**：基数 `maxChars` 300，自定义只能 ≤300；想放宽必须改基座，这不在群设置里做。

### 4.3 自进化：标签建议

自定义标签不该全靠你手填。青梅会从群的行为里**提议**标签：

```text
观察（30 天窗口，≥50 条消息）
  ├─ 高频实体：合同/报价/交付 → 建议「甲方群」，基座 client
  ├─ 时间分布：工作日 9–18 点为主，周末静默 → 佐证 work
  └─ 成员重叠：与已有「公司内部」群成员重合度 >60% → 反对 casual
        ↓
  提议：{ label, base, note, evidence, 预计影响 }
        ↓
  你在端上确认一次（可改备注）
        ↓
  之后同类群自动套用该标签（可撤销），并留审计
```

纪律：

- 建议**从不自动应用到未配置群**——未配置群永远先走「权限未配置」，直到你确认。
- 同一条建议被拒两次就不再提（写进画像偏好）。
- 自动套用只对"同渠道 + 成员重合度 >60% + 消息特征相似"的新群生效。
- 标签本身是 B 类策略数据，改它不需要发版；备注入 prompt 属于 C 类，可热更。

策略字段（`Policy`）：

```ts
interface Policy {
  memory: { audiences: string[]; projectScoped: boolean }
  tools: { allow: string[]; deny: string[] }
  reply: { maxChars: number; tone: 'formal' | 'neutral' | 'casual'; proactive: boolean }
  data: { maxSensitivity: 'public' | 'private' | 'secret' }
}
```


## 5. 关键设计：策略在组装上下文时执行，不停留在提示词

最弱的做法是在 prompt 里写"不要透露任务进度"——模型可能被绕过、可能口误、可能被提示注入。

青梅的做法是：**在把上下文交给模型之前，就把不该给它看的数据裁掉。**

```text
入站消息
  → 会话画像（tags）
  → policy.resolve(profile)  →  PolicyEnvelope
  → 上下文组装（memory.recall 带 audience 过滤 + 工具清单裁剪）
  → 交给模型
```

吹水群里，模型**根本拿不到**任务与日程数据。"不能说"变成了"没有可说的"，
这比任何提示词都可靠。

## 6. 回复信封

```ts
interface PolicyEnvelope {
  allowedClaims: string[]      // 这次允许陈述的内容类别
  forbiddenTopics: string[]    // 明确禁止的话题（同时用于后置校验）
  maxChars: number
  tone: 'formal' | 'neutral' | 'casual'
  refusalStyle: 'brief' | 'redirect-dm' | 'ask-owner'
}
```

信封同时给两方用：给模型当约束（prompt 前缀），给输出校验当判据（后置闸）。
它是策略求值的产物，不是手写文案。

## 7. 完整走查：「项目进度到哪了」

**在工作群里**

```text
消息 → tags=[work] → envelope {
  allowedClaims: ['task-progress', 'schedule-of-owner'],
  maxChars: 300, tone: 'neutral'
}
→ recall(scope: project:qingmei, audience: group:feishu_xxx)
→ 命中 2 条任务进度 → 模型生成「重构已完成 70%，卡在发布脚本」
→ 输出校验：无 forbidden、长度 42 字 → 发送
```

**在吹水群里**

```text
消息 → tags=[casual] → envelope {
  allowedClaims: [],
  forbiddenTopics: ['task', 'schedule', 'memory'],
  maxChars: 100, refusalStyle: 'brief'
}
→ recall 只回 public（通常为空）
→ 模型：没有任务上下文，只能给一句「这个在群里不方便说，私聊我」
→ 输出校验：确认没有出现任务名/进度 → 发送
```

差别不在"模型是否听话"，而在**模型看到的东西不同**。

## 8. 后置校验

第二道闸，防止模型自行发挥：

- 文本中出现 `forbiddenTopics` 关联的实体（任务名、项目名、联系人）→ 拦截并改写为拒绝话术
- 超过 `maxChars` → 截断
- 出现疑似敏感模式（手机号、身份证、链接到内网）→ 拦截
- 命中拦截时记 `qm_audit`，并在后台"群管理"里可见（让你知道它差点说错）

## 9. 后台：群管理页

网页后台的一个页面，解决"我怎么知道有哪些群、它们是什么"：

| 区域 | 内容 |
| --- | --- |
| 列表 | 群名、渠道、成员数、标签、状态、最近活跃、最近 7 天消息数 |
| 详情 | 标签编辑、"这个群里我能看到什么/能做什么"的实时预览、策略覆盖 |
| 拒绝记录 | 最近被拦下的回复（脱敏），用于调策略 |
| 批量 | 按渠道筛选、批量打标、批量静音 |
| 危险操作 | 退群、拉黑、清空该群记忆 |

三条交互原则：

1. **预览优先**：改标签前先看到"改完会发生什么"，不要让人盲改。
2. **默认安全**：未配置群一行字都读不到。
3. **改动留痕**：谁在什么时候改了什么，进审计。

## 10. 与权限、记忆 Audience 的关系

| 层 | 回答什么问题 |
| --- | --- |
| `conversation` 画像 | 这个群是什么类型 |
| `permission` | 这个人能不能做这个动作 |
| `memory.audience` | 这条记忆能不能被这个视口看到 |

三者串联：画像 → 策略信封 → 召回过滤 → 输出校验。
**画像不是权限的替代品**，它只是给权限提供"场景参数"。

## 11. 指标

| 指标 | 目标 |
| --- | --- |
| 未配置群泄露 | 0 |
| 群标签覆盖率（活跃群） | 100% |
| 误拒率（该答却拒） | ≤ 5%，按周复盘 |
| 后置拦截率 | 持续下降（说明上下文裁剪到位） |
| 配置耗时 | 从入群到配好 ≤ 2 分钟 |

## 12. 里程碑

| 阶段 | 内容 | 工期 | 验收 |
| --- | --- | --- | --- |
| **G1** | 群发现 + 画像存储 + 后台列表/打标 | 1 周 | 邀请进群 30 秒内出现在后台，打标后立即生效 |
| **G2** | 策略求值 + 上下文裁剪 + 回复信封 | 1 周 | 同一问题在工作群/吹水群得到不同结果，且吹水群上下文里**无任务数据** |
| **G3** | 后置校验 + 拒绝记录 + 覆盖配置 | 1 周 | 注入 50 条 private 记忆，吹水群 0 泄露 |
| **G4** | 自定义标签（继承 + 备注）+ 标签建议 + 自动套用 | 1 周 | 新群自动获得合适标签；误判可一键撤销并记住 |

G1–G4 接在 M3（QQ 与飞书）之后，约 4 周。
