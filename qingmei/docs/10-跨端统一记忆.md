# 10 · 跨端统一记忆

> 在电脑上说过的事，手机上必须记得；在工作区里做完的任务，聊天里必须能接上。
> 只要记忆按"端"切分，这个系统就不配叫助理——它只是几个各自失忆的聊天框。

## 1. 问题

多端最容易被做错的一件事：把记忆存进各自的端。

```text
❌ 错误形态：每个端各记一份
   PC ── 记忆A ──┐
   手机 ─ 记忆B ──┼── 互不相通：三个陌生人
   QQ ── 记忆C ──┘

✅ 正确形态：一个记忆，多个视口
   PC / 手机 / QQ / 飞书 / Watch / harness
        └────────┬────────┘
                  ▼
          青梅记忆中枢（唯一事实源）
```

端上只允许有**缓存**（为了离线与延迟），不允许有**独立记忆**。
缓存与中枢不一致时，以中枢为准；缓存负责"断网时还能用"，不负责"我知道你不知道的事"。

## 2. 原则

| # | 原则 | 含义 |
| --- | --- | --- |
| P1 | **一个记忆，多个视口** | 存储全局；渠道只决定"能不能看、看多长"，不决定"记不记得" |
| P2 | **会话是上下文边界，不是记忆边界** | session 只影响 token 窗口与隐私，记忆按 actor/thread 归集 |
| P3 | **上报结论，不上报过程** | harness 报的是"改了什么、为什么、结论"，不是几万行日志 |
| P4 | **默认全局，仅设备属性落设备域** | 个人事实（过敏、生日）必须全局；"这台机器用 pwsh"才落设备域 |
| P5 | **多源印证提升可信度** | 同一事实被两个端/两个来源说出来 → 置信度上升，而不是存两份 |
| P6 | **服务端时间为准** | 端上时钟不可信；排序、冲突都用中枢接收时间 |

## 3. 拓扑

```text
 通道适配器            端宿主                    执行体
 QQ/飞书/Web/App/Watch   PC(Web/EXE)  手机(APK)   DSH/ZCode（harness）
        │                    │            │              │
        └──── MCP / REST ────┴────────────┴──── MCP ─────┘
                              │
                    ┌─────────▼──────────┐
                    │  memory.ingest()   │  幂等写入
                    │  memory.recall()   │  统一召回
                    └─────────┬──────────┘
                              ▼
                     神经元图（全局唯一）
```

- 所有生产者走同一个 `ingest`，所有消费者走同一个 `recall`。
- **没有第二条写入路径**（比如"手机端直接写本地库"），否则一定会分叉。

## 4. 数据模型增量

在 [09](09-神经元记忆核心.md) 的 `qm_neuron` 上补四组字段：

```sql
ALTER TABLE qm_neuron ADD COLUMN origin_kind  TEXT;  -- channel | harness | self | doc | schedule
ALTER TABLE qm_neuron ADD COLUMN origin_id    TEXT;  -- 消息 id / TaskRun id / incident id
ALTER TABLE qm_neuron ADD COLUMN device_id    TEXT;  -- 可选：设备属性类记忆
ALTER TABLE qm_neuron ADD COLUMN audience     TEXT;  -- owner | family | group:<id> | device:<id>
ALTER TABLE qm_neuron ADD COLUMN dedupe_key   TEXT;  -- 规范化后的去重键

CREATE TABLE qm_memory_event (          -- 幂等日志：同一条上报只应用一次
  idempotency_key TEXT PRIMARY KEY,
  source          TEXT NOT NULL,
  payload_hash    TEXT NOT NULL,
  applied_at      INTEGER NOT NULL,
  neuron_ids      TEXT NOT NULL
);

CREATE TABLE qm_memory_provenance (     -- 一个神经元可以被多个来源印证
  neuron_id  TEXT NOT NULL,
  origin_kind TEXT NOT NULL,
  origin_id  TEXT NOT NULL,
  observed_at INTEGER NOT NULL,
  PRIMARY KEY (neuron_id, origin_kind, origin_id)
);

CREATE TABLE qm_thread (                -- 跨端任务/话题的缝合点
  id         TEXT PRIMARY KEY,
  title      TEXT,
  task_id    TEXT,
  created_at INTEGER NOT NULL
);
```

`audience` 在**写入时**就确定，而不是召回时才判断——两层都做，防群聊泄露。

## 5. 写入：四类来源

| 来源 | 典型事件 | 报什么 |
| --- | --- | --- |
| **channel** | 用户说"我下周三去杭州" | 事实 + 情节（原话摘要） |
| **harness** | 任务完成、阶段结论、决策 | 任务记忆：改了什么、为什么、留下什么风险 |
| **self** | 故障、修复、回滚 | incident + 根因 + 补丁（供 playbook） |
| **doc / schedule** | 导入文档、日程变更 | 实体与事实，不存全文 |

### 5.1 任务记忆上报（harness → 青梅）

PC 端的工作区任务结束后，通过 MCP 调 `qm_finish_task`，**同时**提交结构化记忆。
这是"电脑上做完的事，手机上能接着聊"的关键。

```json
{
  "runId": "run_01J8X2",
  "status": "done",
  "summary": "CI 从 12 分钟压到 4 分钟",
  "memory": [
    { "kind": "fact",     "subject": "project:qingmei", "predicate": "构建耗时", "object": "4 分钟",
      "confidence": 0.9,  "sensitivity": "private" },
    { "kind": "decision", "text": "CI 缓存改用 pnpm store，不再缓存 node_modules", "confidence": 0.95 },
    { "kind": "lesson",   "text": "缓存 node_modules 在 workspace 下会因锁文件变化整体失效", "confidence": 0.8 },
    { "kind": "artifact", "text": "PR #128 已合入", "ref": "github:zy-game/qingmei#128" }
  ],
  "links": [
    { "fromKey": "project:qingmei|构建耗时", "toKey": "project:qingmei", "kind": "associative", "weight": 0.7 }
  ]
}
```

三条硬规则：

1. **只报结论，不报过程**。过程留在会话转录里，按需检索；否则记忆会被日志淹没。
2. **必须带 `runId`**。它同时是幂等键与线程缝合点。
3. **结构性字段优先**。能写成 `subject/predicate/object` 的就不要写自由文本，否则以后无法合并。

### 5.2 幂等

`idempotency_key = sha256(source + runId/messageId + payload_hash)`。
重复上报（网络重试、双端同步）只应用一次，返回已存在的 neuron id 列表。

## 6. 去重与合并

同一件事从两个端进来是常态：手机上说了，PC 上的任务也产出了同样的结论。

```text
上报 ──▶ 规范化（小写、数字/日期转绝对、去语气词）
      ──▶ dedupe_key
      ──▶ 已存在？
            ├─ 是：不新建。provenance 追加来源；confidence = max(old, new) + 0.05×新增来源数（上限 0.99）
            └─ 否：新建 neuron，建边
```

- **合并而不是覆盖**：旧值不删，置 `valid_to`，与新值建 `contradiction` 边（沿用 [09](09-神经元记忆核心.md) §6）。
- **跨源印证加分**：同一事实被 owner 私聊 + 任务结论同时确认，比单源更可信。
- **情节按时间窗聚类**：同一个会议在三个端各有一段转写 → 先按时间 + 实体聚类，再抽事实，避免生成三条重复情节。

## 7. 冲突与优先级

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 用户显式纠正 | "不对，是周四" —— 立刻生效，旧值进矛盾边 |
| 2 | 更晚发生 | 时间优先于来源，但要看 `occurredAt` 而不是接收时间 |
| 3 | 来源可信度 | owner 私聊 > harness 任务结论 > 群聊 > 模型推断 |
| 4 | 设备上下文 | 与某台机器强相关的，落设备域，不与全局冲突 |

第 4 条是避免"假冲突"的关键：**"这台机器用 pwsh" 和 "我用 zsh" 并不矛盾**，
前者是设备属性（`device_id`），后者是个人偏好（全局）。

## 8. 读取：同一记忆，不同视口

召回引擎只有一个，差异只在**过滤**与**呈现预算**：

| 视口 | 过滤 | 预算 | 呈现 |
| --- | --- | --- | --- |
| 私聊 / 个人端 | `audience ∈ {owner, family}` + 全局 | 600–1200 token | 完整 |
| 群聊 | 仅 `audience = group:<id>` 或 public | 300 token | 简短，不提私事 |
| Watch | 同上 + 强制摘要 | 一句话 | 口播 / 一行字 |
| Harness | 任务相关 + 项目域 | 按任务 | 结构化事实 |

**设备上下文加成**：当前设备相关的设备域记忆 +0.1 分；但**个人事实永远全局可见**，
不因换端而消失——这是"不能失忆"的底线。

## 9. 线程缝合：跨端任务

用户在 PC 上开了一个任务，晚上在手机上问"那个重构怎么样了"——必须接得上。

```text
qm_task ──┬── TaskRun（PC, harness 会话）
          ├── 消息（手机，提到"重构"）
          └── 日程（"周五前完成"）
                └── 都挂到同一个 qm_thread 节点
```

实现：任务创建时生成 `thread_id`；之后任何渠道/任何 harness 只要提到该任务实体，
抽取阶段就把新节点连到 thread 节点。召回时命中 thread → 扩散到全部关联节点。

验收口径很简单：**在 A 端做的事，B 端问一句能答上来。**

## 10. 离线、重连、时钟

离线冲突不是一个问题，是三个。它们的策略完全不同，混在一起谈会做错：

| 冲突类型 | 场景 | 谁赢 | 数据后果 |
| --- | --- | --- | --- |
| **记忆写入** | 手机离线说"改到周四"，PC 离线说"改到周五" | 服务端接收时间**后到者**生效 | 被覆盖者保留为历史 + `contradiction` 边，可追溯 |
| **任务状态** | 手机标记任务完成，PC 上的 TaskRun 还在跑 | **服务端状态唯一权威**，客户端乐观 UI 回滚 | 以 TaskRun 状态机为准，冲突时通知用户 |
| **待发消息** | 离线发了三句，恢复后重放 | 幂等键**只保留第一次** | 不重复发送、不重复入库 |

三个层次的区别：

- 记忆冲突是**认知冲突**——两种说法都可能是真的，所以保留历史、不删任何一方。
- 任务状态是**状态冲突**——同一时刻只能有一个真值，所以必须有一个权威（服务端）。
- 消息重放是**传输冲突**——同一件事被送了两次，所以去重即可，不涉及语义。

实现要点：

- **记忆**：`occurredAt`（设备说的时间）只作展示；排序与冲突判定一律用 `receivedAt`。
- **任务**：客户端不做状态机，只做展示与"请求变更"；所有状态迁移在服务端完成。
- **消息**：outbox 每项带 `idempotencyKey`，服务端返回已存在的 neuron/message id 供本地对齐。
- **时钟**：设备时间漂移超过 5 分钟时，界面标注"时间可能有误"，但仍按服务端时间归序。

## 11. 隐私：全局不等于人人可见

"全局记忆"是**同一个存储**，不是**同一个可见范围**。

| 场景 | 处理 |
| --- | --- |
| 家庭共享 | `audience = family` 的可见；个人私事 `audience = owner` |
| 群聊 | 只注入 `group:<id>` 与 public；私聊内容绝不外溢 |
| 工作机 | **不做设备隔离**：工作与个人的记忆统一；只有「设备属性」（路径、工具链、已装软件）随上下文带上，不构成隐私边界 |
| secret | 沿用 [04](04-记忆数据与隐私.md) 矩阵：本地加密、不进云、不出渠道 |

写入即定 `audience`，召回再校验一次——两道闸，任何一道漏了都不至于泄露。

## 12. 失败模式

| 失败 | 现象 | 对策 |
| --- | --- | --- |
| 双写重复 | 同一事存了两份，召回时重复回答 | 幂等键 + dedupe_key 双保险 |
| 时钟漂移 | 事件顺序错乱，"先答应后反悔"反了 | 中枢时间排序 |
| 离线冲突 | 两端各改一条事实 | 后到者生效，被覆盖者留矛盾边 |
| 群聊泄露 | 群里提到私事 | 写入定 audience + 召回再校验 |
| 碎片化 | 三个端各报一段，同一会议三条情节 | 时间窗 + 实体聚类后再抽取 |
| 视口漂移 | 手表上答案和网页不一致 | 同一召回结果，仅预算不同；摘要由同一结果裁剪 |

## 13. 指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 跨端一致率 | A 端说过的事，B 端提问能答对的比例 | ≥ 95% |
| 重复率 | 同一事实对应的 neuron 数 | ≤ 1.05 |
| 缝合成功率 | 跨端任务被正确归入同一 thread 的比例 | ≥ 90% |
| 同步延迟 | PC 任务完成 → 手机可召回 | ≤ 5s（在线） |
| 泄露事件 | 群聊/他人看到本不该看的记忆 | 0 |

## 14. 里程碑

| 阶段 | 内容 | 工期 | 验收 |
| --- | --- | --- | --- |
| **N1** | 统一 `ingest`/`recall` + 幂等 + provenance + 去重 | 1 周 | 同一事实从两个端上报，库里只有一条，置信度上升 |
| **N2** | harness 任务记忆上报 + thread 缝合 | 1 周 | PC 上跑完任务 → 手机上问"进展"能答出结论 |
| **N3** | 离线缓存 / 重放 / 增量同步 | 1 周 | 飞行模式说三句话，恢复后全部入库且不重复 |
| **N4** | 视口过滤（群聊/watch）+ 泄露测试 | 1 周 | 群聊注入测试 0 泄露；watch 答案与网页一致（仅长度不同） |

N1–N4 共 4 周，接在 M1（记忆基础）之后，与 N（神经元引擎）可并行——
引擎管"怎么记"，本节管"谁在记、给谁看"。
