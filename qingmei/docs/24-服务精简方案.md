# 青梅服务与插件精简方案

## 0. 结论

当前问题不是“插件架构错了”，而是三层混在一起：

```text
基础设施：store/channel/gateway/task/approval...
个人助手能力：对话/记忆/身份/日程/技能...
实验能力：内容/复盘/主动开场/督促/休息...
```

优化原则：

1. **能确定性处理的，不调用 LLM。**
2. **能由 DSH 执行器保留的会话状态，不再在青梅重复建模。**
3. **一个能力只保留一个 owner 服务。**
4. **门面包、纯转发包、无消费者的服务删除。**
5. **实验模块移出默认装配，不参与核心计数。**

## 2. ZCode Memory 的事实

ZCode 的 Memory：

```text
~/.zcode/cli/memories/projects/<project>/memory/
├── MEMORY.md
└── *.md
```

它不是向量库，而是：

```text
模型后台回顾最近对话
→ 写成 Markdown 事实
→ 更新 MEMORY.md 索引
→ 下个会话加载索引
```

官方文档还说明：

- Memory 默认关闭
- 可能发起额外模型请求，增加 Token 用量
- 按项目隔离
- 索引有大小上限

所以“ZCode 有记忆”不能作为“向量库更便宜”的论据。  
它反而说明：**记忆成本主要来自模型提取，不是存储。**

参考：[ZCode Memory 文档](https://zcode.z.ai/cn/docs/memory)

## 3. 记忆方案选择

### 不推荐

```text
每轮对话都让 LLM 抽事实
+ 自建 synapse / episode / working memory
+ 自建 hash embedding
+ 自建向量召回
```

这是当前 `provider-memory-sqlite` 的复杂度来源，成本高、难维护。

### 推荐

第一阶段：

```text
显式记忆：
  用户说「记住 …」/「忘掉 …」
  → 直接写 Markdown / SQLite 事实
  → 不做后台 LLM 抽取

检索：
  SQLite FTS5
  （当前 store 已经在用 SQLite，不需要新服务）
```

第二阶段，只有确实需要语义召回时再加向量：

| 方案 | 优点 | 代价 |
|---|---|---|
| `sqlite-vec` | 与 SQLite 同库，专用向量索引 | Node/Electron 原生扩展加载 |
| `@orama/orama` | 纯 JS、全文 + 向量混合检索、可持久化 | 不是专用向量数据库 |
| `@lancedb/lancedb` | 成熟向量库、检索能力强 | 原生依赖、体积大 |
| 外部 Qdrant/Chroma | 能力强 | 多一个服务，个人部署过重 |

建议：

```text
先 SQLite FTS5 + Markdown 事实
确有语义需求再上 Orama 或 sqlite-vec
不引入需要独立进程的向量服务
```

## 4. 服务取舍

### 删除（无消费者/纯门面）

| 对象 | 原因 |
|---|---|
| `service-store` | 运行时无行为，契约已在 core；provider 直接用 core |
| `service-llm` | 运行时无行为；若后续去掉 LLM，整个删除 |
| `service-memory` | 运行时无行为；契约已在 core |
| `provider-permission-static` + `permission` 服务 | 当前没有消费者；DSH 权限走 approval |
| `provider-embedding-openai` | 默认未装配；先不引入向量依赖 |

### 合并

| 当前 | 合并后 | 说明 |
|---|---|---|
| `qm-skill` + `qm-skill/api` | `qm-skill` 单插件 | API 路由直接在同插件注册 |
| `provider-audit-sqlite` + `qm-audit` | `qm-audit` | 服务实现 + HTTP 面同一插件 |
| `provider-schedule-sqlite` + `qm-reminder` | `qm-schedule` | 日程账本 + 到点投递 |
| `qm-history` + `qm-thread` | `qm-history` | 消息、turn、thread 同一历史域 |
| `provider-task-sqlite` + `qm-task` | `qm-task` | 任务账本 + 调度 + HTTP；仍保留可替换接口 |
| `provider-approval-sqlite` + `qm-approval` | `qm-approval` | 审批队列 + 渠道推送 + HTTP |

### 移出默认装配

| 插件 | 处理 |
|---|---|
| `qm-autonomy` | 实验/可选；主动建议不是主链路 |
| `qm-incident` | 实验/可选；自愈不是主链路 |
| `qm-conversation-profile` | 可选；群策略不是主链路 |
| `qm-consolidate` | 随记忆简化删除 |
| `qm-memory-extract` | 随 LLM 抽取删除 |
| `qm-device` 的 digest/lessons LLM 部分 | 删除；只保留设备/任务协议 |

```text
qm-device
qm-approval

qm-skill
service-persona
```


## 5. AI 边界

### 允许 AI

```text
DSH Executor：
  对话、工具调用、代码执行

可选 utility LLM：
  显式总结/分类/复盘
  但默认关闭，不进入每轮对话
```

### 不允许 AI

```text
记忆事实提取（改为显式记忆/规则）
设备 session lessons（删除）
群策略判定（规则）
身份绑定（规则）
任务状态/依赖/优先级（规则）
审批（规则 + 人）
```

## 7. 实施顺序

### Phase 1：删无消费者

```text
删除 permission 服务/provider
删除 service-store/service-llm/service-memory 门面包
更新 imports 到 core
```

### Phase 2：删 AI 后处理

```text
删除 qm-memory-extract
删除 qm-device 的 optimize/distill
qm-agent 去掉 LLM 对话回退（DSH only）
```

### Phase 3：重写记忆

```text
provider-memory-sqlite：
  Markdown/SQLite FTS5
  显式 ingest/forget
  删除 synapse/episode/working/consolidate
qm-consolidate 删除
```

### Phase 4：合并插件

```text
skill + api
audit provider + api
schedule + reminder
history + thread
task provider + runner
approval provider + api
```

### Phase 5：对话 Task 化

```text
qm-agent → qm-conversation
  → TaskService
  → DSH Executor
  → reply sink
删除 qm-agent 包
```
