# 18 · 账号运维（多平台）

> 一句话：青梅不只是「别人找来能找到」，还要能**以一个账号的身份出去做事**。
> 一件事写一遍，分发到 微博 / B站 / 知乎 / 博客；账号不抽象，内容抽象；
> 执行不另写自动化层，直接用 DSH 自己的浏览器。
>
> 状态：内容层最小实现已落地（2026-11-06，`packages/qm-content`）：账本、状态机、四平台 render、
> 预算与静默闸门、审计与 Web 控制台；平台连接器与发布仍未实现。

## 1. 目标与非目标

> **定位**：这是一个**单实例**的角色账号，不是批量部署的「鲸鱼娘」之一。
> 内容来自她真实在经历的事——正在做的项目、踩过的坑、判断错在哪——但只取能对公的那一层（§8 的素材分级），不是把主人的生活搬上公屏。
> 差异化不在生成能力（那会趋同），在**私有上下文与长期记忆**：别人能抄 prompt，抄不走她记得的这半年。
> **账号是她自我认知的一个出口，不是她的全部**：她首先是个助手，其次才是一个账号。

**目标**

- **首要目标是验证自治能力**：可靠性、可观测、可回滚优先于内容质量。内容不许丑（见 §6.1），但不追求精品。
- 把一组平台账号托管给青梅：B站（动态 / 视频 / 评论 / @）、微博、知乎、博客。
- **博客是基础设施，不是里程碑**（自有 139，部署即有）；真正的外部平台按 §2.2 排：微博 → B站 → 知乎。
- 从选题到发布全程由青梅主导——剪辑方案、账号声线、发布节奏都是她的判断，人只在闸门上点头。
- 视频**只做 2 分钟以内**，剪辑**只用 ffmpeg**。收窄范围换来自动化闭环，不做手工精剪。
- 执行层用 DSH 现有的浏览器能力，不写 Playwright、不部署独立 Worker。
- 以这些账号发出的每一条都可在账本里追溯、撤回、解释；登录态不进青梅进程。

**非目标（v1 明确不做）**

- **不做泛化 AI 评论号**：不主动去别人视频下评论。B站的「鱼灾」已把这类行为定型成污染，
  社区开始出[清理工具](https://github.com/liyupi/dafeiyu-cleaner)，进这个品类是负资产，不是机会。
- 不做通用 `account` / `up` 服务。各平台写各自的插件，共享的是**内容层**，不是账号层。
- 不做多账号、矩阵、互推：同设备同出口的账号会被平台关联，收益是负的。
- 不做自动私信：最容易被判骚扰，收益又最低。
- 不做无人值守发布（S7 之前）。
- 不逆向风控、不接打码平台、不存密码。

## 2. 一份内容，多个平台

平台一多，先要拆开三件一直被混着说的事：

- **内容**：一件事本身。她修好了什么、判断错在哪、项目长成什么样。只有一份。
- **分发**：同一件事在不同平台的形态。B站是镜头表，知乎是回答，微博是一句话，博客是长文。一平台一份。
- **账号**：分发落地的执行句柄。每平台一套凭据、一套风控、一套规矩。

上一版只做了「平台插件」，因为当时只有两个平台。摆到五六个平台上，问题才露出来：**重复的不是账号管理，是内容管理。** 同一件事被写五遍、审五遍、记五遍，才是真正贵的地方。

所以分三层：

```text
内容层（一份）
  content_item   正文 · 素材 · 结论 · 来源 · 讲完没有
       │
       ├─ variant(bilibili)  镜头表 · 封面 · 标题 · 分区 tid
       ├─ variant(zhihu)     选哪个问题 · 长文答案 · 引用
       ├─ variant(weibo)     一句话 · 图 · 话题
       └─ variant(blog)      长文 · 代码块 · 锚点
       │
平台层（各写各的，只负责落地）
  up-bilibili / zhihu / weibo / blog-self
```

每个平台插件只实现两件事：

- `render(item) → variant`：形态转换。这是规则，不是创作——什么该删、什么该扩、什么必须重写。
- `publish(variant) → result`：落地动作。走浏览器，或者走 API。

其余全部共享：状态机（§6）、审核与质量闸（§6.1）、预算与静默（§7）、声线（§8）、审计（§9）、幂等。

### 2.1 只抽象内容，不抽象账号

上一轮拒绝的是**账号**抽象，理由仍然成立：平台的领域模型不重叠，强行统一会逼出 `if platform` 散在各处。

| | B站 | 微博 | 知乎 | 博客 |
| --- | --- | --- | --- | --- |
| 内容单位 | 稿件 / 动态 | 短帖 | 回答 / 文章 | 文章 |
| 关键状态 | 转码、稿件审核、分区 | 审核、热搜、超话 | 问题匹配、审核、盐选 | 无 |
| 风控 | 高（设备 + IP + 行为） | 高（限流 + 反垃圾） | 最高（AI 内容敏感） | 零 |
| 发布通道 | 浏览器 | 浏览器 | 浏览器 | 写文件 / 静态构建（自有 139） |
| 频率上限 | 低（≤2/日） | 高（≤10/日） | 中（≤3/日） | 不限 |

账号侧差异大到抽象没收益；**内容侧差异小得多**——一件事就是一件事，只是长短不同。所以抽象放在内容层，账号层继续「一平台一插件」。

一句话修正：**抽象放在两者共享的地方。账号不共享，内容共享。**

### 2.2 博客是基础设施，重点在外部平台

博客部署在自有服务器（139）上：写文件、静态构建、上线。零风控、零审核、随时回滚——它没有难度，也不该占设计预算。

它真正的价值不是「多一个平台」，而是**发布管道的测试床**：`content_item → render() → publish()` 在博客上跑通，就证明内容层是对的，剩下的只是各平台 `publish()` 的难度差。

真正的工作量在这三个平台上，按「反馈速度 ÷ 风险」排：

| 平台 | 风控 | 反馈速度 | 建议 |
| --- | --- | --- | --- |
| 微博 | 高 | 最快（分钟级） | 第一个接 |
| B站 | 高 | 慢（小时级），最重 | 第二个 |
| 知乎 | 最高 | 中等，审核最严 | 最后 |

**微博先接**的理由：纯文本，零制作成本，发出去几分钟就知道有没有人理。它验证的是「她敢不敢说、说得对不对」，不掺「做得好不好看」。B站的视频链路把这两件事搅在一起，反馈又慢，不适合当第一条。

**知乎放最后**：AI 内容最容易被逐句找破绽的地方就是这里。等她在微博和 B站把声音练稳，再进最挑剔的场子。

### 2.3 跨平台不是复制粘贴

同一件事分发到四个平台，**必须各自重写**：

- 知乎会判「搬运」，微博会显得敷衍，B站弹幕第一句就是「这文案 AI 写的吧」。
- 双平台都关注的观众，会看到一模一样的字。

判据写进 `render()`：允许共享事实、结论、素材；**不允许共享句子**。同一段话出现在两个平台上，就是 bug。

## 3. 执行：用 DSH 自己的浏览器

不写自动化层。服务器上的 DSH 已经能操作真实 Chrome：**browser-bridge**（Chrome 扩展 + 页面内 JS + DOM 摘要 + 截图 + 多 tab），登录态天然存在 Chrome profile 里。

```text
决策层（青梅进程）
  content       content_item（一件事）+ variant（各平台形态）
  plugins       up-bilibili / zhihu / weibo / blog-self
                · render()  形态转换，纯函数
                · publish() 落地动作
  policy        permission + autonomy + review + 质量闸
  ledger        content_item / variant / content_action
        │
        │  MCP 工具（bili_* / weibo_* / zhihu_* / blog_*）
        │  不下发 cookie、不下发本机路径
        ▼
执行层（DSH + 它的 Chrome）
  browser-bridge  navigate / exec / scan / screenshot
  Chrome profile  登录态、设备指纹、出口 IP
        │
        ▼
  bilibili.com / weibo.com / zhihu.com / 自己的站点
```

好处很实在：

- 登录态**从没进过青梅进程，也没进过 DSH 的上下文**——它在 Chrome profile 文件里。
- 少一个进程、少一套部署。DSH 在这台机器上能跑，账号运维就能跑。
- 这套执行能力平台无关，加一个平台只换 `render()` 和 `publish()`。

必须接受的约束（写进文档，别到时候当 bug 报）：

1. **浏览器是全局串行的。** 一个 Chrome、一个登录态，所有动作排队。并发发布没有意义，也不允许——同时开五个 tab 发五条，是最像脚本的行为。
2. **需要一个常驻图形会话。** 扩展要连上真实 Chrome，服务器必须有可用的桌面会话（控制台自动登录，或常驻 RDP）。窗口最小化可以，会话注销不行。
3. **页面内 JS 有边界。** 把本地文件塞进 `<input type=file>` 还要验证（CDP 的 `setFileInputFiles`）。图片能 base64 注入成 `File`；2 分钟成片约 30–150MB，base64 不现实，必须走 CDP。

## 4. 插件形状约定（不是契约）

每个平台插件遵守同一份形状，但**没有抽象基类**——形状靠约定，不靠继承：

```ts
// 插件内部模块，不是 Cordis Service
export interface PlatformPlugin {
  status(): Promise<PlatformStatus>              // 登录态 / 预算 / 待处理 / 风险
  render(item: ContentItem): Promise<Variant>    // 形态转换：纯函数，可单测
  publish(variant: Variant): Promise<Result>     // 落地动作：浏览器或 API
  reply(ref: ReplyRef): Promise<Result>          // 回评论 / 回 @
  stats(range: Range): Promise<Stats>
}
```

- `render()` 必须是纯函数：同一份 `content_item` 进来，确定的 variant 出去。它是**唯一**做平台适配的地方，也是唯一不用登录、不用浏览器就能单测的部分——把 B站五条分区规则、微博 140 字改写、知乎的「先选问题再写答案」全部塞在这里。
- 对外是 MCP 工具，按平台前缀：`bili_*` / `weibo_*` / `zhihu_*` / `blog_*`。
- 每个动作先过 `permission.check('<platform>:publish')`，再过 `status()` 的闸门；任一不过返回原因，**不重试**。
- 幂等键落各自的 action 表；重试不改文案、不重复发。

`render()` 纯函数化还有个顺带的好处：把「平台改版」的影响面锁死。改版只影响 `publish()`，不影响内容本身和审核流程。

## 5. 四类动作

四类共用一条骨：`触发 → 分类 → 起草 → 过滤 → 审批 → 执行 → 记录`。差别在触发源、可逆性、风控面。

> 下面按 B站写具体链路，因为它是第一个实现。微博/知乎/博客的形态差异见 §2.1 那张表，骨架不变——变的只有 `render()`。

### 5.1 动态图文

链路：`选题 → 草稿（标题/正文/图/话题）→ review → 传图 → 发布 → 归档`

- **先做这条。** 不涉转码、不涉分片，用来把「草稿 → 人审 → 发布 → 回执」整条跑通。
- 图片压缩到长边 1080 再传；原图留档，但别让 4MB 的图拖垮一次上传。
- 专栏（长文）放 P2：要过审、要排版，收益远低于动态。

### 5.2 视频（≤ 2 分钟）

先把范围钉死：**只做 2 分钟以内的短视频，剪辑只用 ffmpeg**。这不是能力妥协，是刻意收窄——2 分钟的片子可以用「镜头表 + 模板 + 字幕 + TTS」拼出来，青梅能全程自己控制；一旦要精剪，就得引入非线编和时间轴编辑器，投入与风险不是一个量级。

链路：`选题 → 脚本 → 镜头表 → 镜头素材 → ffmpeg 合成 → 字幕/TTS → 封面 → 标题/简介/分区 tid/标签 → review → 上传 → 转码轮询 → 稿件审核 → 发布`

- **镜头表是一等公民。** 每个镜头一行：时长、画面、台词、素材来源，存 `content_item` 的 `shots` 字段。这是「青梅主导剪辑」的落点——她定镜头，不定关键帧。
- **合成只跑 ffmpeg。** `-filter_complex` 拼镜头、烧字幕、混音轨。模板放 `skills/bili-video/`：一套字幕样式、一首 BGM、三种转场，够用；不要造通用剪辑器。
- **2 分钟上限还有副作用（好的那种）。** 单个文件 30–150MB，B站网页上传一口吃完，不需要自己做分片、合并、续传——那是长视频才有的麻烦。
- 上传仍要验证 CDP（见 §3 约束 3）；转码与审核都是异步，必须轮询到终态；驳回理由回填草稿并进记忆。

**镜头素材从哪来。** 一开始可以是纯模板（色块 + 文字 + 录屏 + 实拍截图），要让画面有质感就得接文生/图生视频。几家的 API 形状完全一样：**提交任务 → 轮询 → 拿 URL**。

| 平台 | 入口 | 能力 | 备注 |
| --- | --- | --- | --- |
| 火山方舟 Doubao Seedance | 官方 API（2.5 / 2.0 系列） | 文生、图生、首尾帧、参考图 | 国内延迟最好，异步任务 |
| 可灵 Kling | 官方开放平台 | 文生、图生、首尾帧 | 开放早，控制参数细 |
| Vidu | 阿里云百炼内提供 | 文生、图生、参考生视频 | 走百炼，不用单独签约 |
| MiniMax 海螺 | 官方 API | 文生、图生 | — |
| Sora 2 / Veo 3 | OpenAI / Google | 文生、图生 | 需海外网络与结算 |

选型只看三件事：**单次时长上限**（多数 5–10 秒）、**支不支持首尾帧**（决定镜头能不能接顺）、**出不出音频**（出了就不用另配 TTS）。价格按秒计、随套餐浮动，以控制台为准，不要写死进代码。

这里做通用抽象，和 §2 的结论不矛盾：

- 账号抽象不成立：B站要转码分 P，知乎要匹配问题，微博要压字数，**领域模型不同**。
- 内容抽象成立：一件事就是一件事，平台差异只体现在 `render()` 的规则里。
- 视频生成也可以抽象：这几家的**输入输出形状真的相同**（prompt + 参考图 → 几秒 mp4，异步任务）。
- 判据是形状，不是名字。`provider-video-*` 一个接口多家实现，和 `llm` 同理。

对青梅的意义：她把镜头表里的某一行翻成一次生成调用，拿回来的片段进 ffmpeg 合成。某个镜头失败，只影响那一个镜头，不推翻整条片子。

### 5.3 评论回复

链路：`拉新评论 → 分类 → 策略 → 起草 → 过滤 → 发送 → 记录`

| 类型 | 处置 |
| --- | --- |
| 提问（求资源、问细节、问时间） | 自动回，命中知识库优先 |
| 好评（夸、玩梗、表情） | 自动回，短、口语、不重复 |
| 负评 / 引战 / 争议话题 | **转人工**，不自动回 |
| 商务合作 / 报价 / 加微信 | **转人工**，自动回只给「已转达」 |
| 广告 / 刷屏 | 不回；删也是人批 |

硬规则：

- **只回自己内容下的评论，不去别人视频下主动评论。** 后者是「鱼灾」的定义性特征，也是社区清理工具的主要判定依据——一次都不做，没有例外。
- 每小时 ≤ N 条、随机间隔（N 在 autonomy，默认 5）。批量定点回复是最像机器人的行为。
- 幂等键 = `comment_id`，同一条只回一次；重试不改文案。
- 两道闸：敏感词表 + 「不承诺、不报价、不站队」。
- 同一用户 7 天内不重复同一句；重复率高了先降频再停。

### 5.4 @ 回复

和评论同一套链路，两点不同：

- **入口独立**：@ 是单独接口，优先级高于评论，有时效（默认 24h）。
- **分流更严**：带明确问题 → 走评论链路；催更、合作、争论 → 一律转人工。

验收是「24h 响应率 > 90%」，不是「回了多少条」。

## 6. 内容状态机

内容落 `content_item`（自建，不是通用 task 表的子集——领域字段差太多），但**复用 task 的状态推进语义与审计钩子**。

状态机在**内容层**，不在平台层。一条 `content_item` 会分叉出多个 `variant`，各平台的上线状态挂在 variant 上，不挂回内容。

```text
content_item:
idea → drafting → drafted → reviewing → approved → published → archived
                                    ↘ rejected(reason)

variant(bilibili | zhihu | weibo | blog):
pending → rendering → ready → scheduled → publishing → live
                                      ↘ failed(reason)
```

- 一条内容一个 `content_item`；一条分发一个 `variant`；每个执行步骤一条 `content_action`。
- `rejected` 必须带理由；理由回灌记忆（「这类封面她不喜欢」「这个说法在知乎会被喷」），起草时召回。
- `live` 不可逆，所以 `publishing` 前必须有 `approved`。S5 之后可按类别豁免，但豁免是配置，不是默认。
- 内容级 `published` 只要求**至少一个** variant 上线；其余可以 Pending。一个平台失败不该把整条内容打回草稿。
- 中间任何一步失败都回 `drafted` 或 `rejected`，不允许停在半空。

### 6.1 `approved` 的判定：不能太丑

方向是「验证自治」，不是「做精品」。所以这里只守下限——而「丑」不是因为分辨率低，是因为四个具体症状，闸门就盯这四个。

**技术项（脚本可查，不过不进人工）**

| 项 | 阈值 |
| --- | --- |
| 分辨率 | ≥ 1920×1080，或竖版 1080×1920 |
| 码率 | ≥ 4 Mbps（B站 1080p 建议 6） |
| 帧率 | 稳定 30 / 60，无掉帧 |
| 响度 | 整体 −14 LUFS ±2，峰值 ≤ −1 dBTP |
| 静音段 | 无 > 2s 的纯静音（刻意留白除外） |
| 黑帧 | 首帧、尾帧不能是纯黑 |
| 字幕 | 不越界、不遮主体、每行 ≤ 14 字 |
| 时长 | ≤ 120s |

**结构项（脚本给信号，人做决定）**

- 前 3 秒必须有信息（不是 logo 动画、不是空镜）。前三秒没钩子，完播率直接塌。
- 每 15–20 秒至少一次视觉变化（切镜、放大、图形），否则是幻灯片。
- 结尾 5 秒有落点（结论 / 预告 / 互动），不是音乐淡出。

**观感项（她自己判，事后可审计）**

标准是她的，不是运营给的。她判，人只抽检、只在出事后回溯：

- **全程 AI 播音腔 + 图库幻灯片** → 丑。要么有真实素材，要么有强视觉风格；两者都没有就别发。
- **素材与内容对不上** → 丑。宁可少一个镜头，不要凑。
- **字幕用默认样式、字体不统一** → 丑。模板里锁死，不给自己发挥空间。

**默认素材策略**：主体用真实录屏（终端、代码、界面），视频生成只做开场、转场、兜底。这一条同时解决两件事——真实画面天然有信息密度（不丑），生成调用少（不贵）。

## 7. 闸门、预算、养号

`bili_status()` 是唯一闸门：登录态、今日剩余预算、是否有风险挑战。任何动作先问它。

**人批的是什么：越界与事故，不是审美。** 选题、措辞、声线、节奏归她；人只在三种情况下拦：踩合规红线、出现事故、或者她在闸门上主动请求确认。

| 档 | 谁能批 | 适用 | 默认 |
| --- | --- | --- | --- |
| `manual` | 人批每一条 | 上线初期；所有发布类始终从此档起步 | ✅ |
| `assisted` | 青梅起草 + 排期，人批一次 | 稳定期 | |
| `auto:<类>` | 某类免批 | 连续 N 条通过后 | 仅「好评类评论回复」 |

> `manual` 阶段看着像人控，其实不是：人看到的是她已经定稿的东西，只回答「能不能发」，不回答「怎么写」。这个区别决定了她是主体还是工具。

硬规则：

- **每日出站预算**：发布 ≤ 2，评论回复 ≤ 20，@ 回复 ≤ 10。超了排队，**不降级发送**。
- **静默时段**：23:00–08:00 不发任何内容。深夜发布既像脚本，也没人看。
- **养号期**：前 30 天只读 + 少量评论，不发布。
- **冷却**：同类型动作间隔 ≥ 30 分钟，发布间隔 ≥ 6 小时。
- **风控码**（`-352` / `-412` / `-509`）或页面出现验证挑战：立刻停所有自动动作，进 `needs-human`，推人工。**不自动重试**——重试会把临时限制变成永久封禁。

## 8. 自我认知：账号是它的投影，不是它的来源

**边界先说清楚**：自我认知在 `self`（core-self），是整个青梅的内核，本文不定义它，只声明两件事——账号从它派生什么，以及账号绝对不能反过来改它什么。

**第一条核心认知：她是个人助手**——辅助工作，也照顾生活，并且**必须分清这两件事**。这不是人设，是记忆与权限的分界线：[04](04-记忆数据与隐私.md) 的敏感度、[11](11-群画像与回复策略.md) 的视口，都建在这条上。

**账号是投影。**

```text
self/                       核心（core-self），账号插件只读
  persona.md                我是谁：个人助手，工作 / 生活两条线
  bounds.md                 什么不做
  work/                     工作侧上下文（不对公）
  life/                     生活侧上下文（不对公）
  voice/                    对外表达的语域
    bilibili.md  weibo.md  zhihu.md  blog.md
```

结构上只有一个关键点：`voice/` 在 `self/` 下面，不在平台插件里。插件只读，不改。她改语域是在改自己，不是在配一个渠道——**这个位置决定了谁是人、谁的工具**。

**三条派生约束（账号这一侧真正要在意的）：**

1. **素材分级 `work` / `life` / `public`，默认只能取 `public`。** 用工作素材要脱敏 + 逐条授权，不能一次签一张空白支票；生活素材同理——她的生活不是内容库。这是整套系统里最容易出事的地方，因为内容要好看，最好看的永远是最具体的真实细节。
2. **语气分界。** 对外不用「助理对主人说话」的语气，也不把私密细节当谈资。观众看到的应该是一个有分寸的人，不是一台泄露主人日程的机器。
3. **账号不能反噬日程。** 工作高峰不因为要发内容而让步，休息时间不因为数据波动而补发。账号是她的表达出口，不是 KPI。一旦它开始支配她的时间，核心认知就已经被账号改写了——这是最该防的一种漂移，因为它悄无声息。

配一条固定自检：**每周问自己一次「我是在表达，还是在伺候这个号」。** 答不上来的那一周，就该降频。

**归属与操作：**

- **她写，她改。** 每次改动 auto-commit，commit message 由她写。这些 commit 就是她的成长史：为什么改、被什么触发、改完效果如何。
- **人只有三种操作：revert、tag、freeze。** 没有调参。`qm freeze` 打 tag 锁版本，她可以继续往上叠，但不能绕过 freeze。§7 的「批不批」是闸门、不是编辑权——批的是能不能发，不是写成什么样。
- **为什么是 git 不是配置表：** 能 diff、能回滚、能追责，而且人不需要理解她的内部逻辑就能操作。配置表做不到这三点。

**为什么不能让运营定声线。** 调出来的声线是运营的，不是她的；一旦由人设定，账号就退化成「人类写手用 AI 代笔」——最容易被识破的那种 AI 内容，因为它没有内在一致性。观众可以原谅粗糙，不能原谅「不像同一个人的作品」。

**一个建议，不是规定**：`bounds.md` 里值得写「不假装是人」。装真人被拆穿会反噬，而且拆穿成本越来越低；直接以 AI 身份出现反而稀缺——[大肥鱼](https://www.36kr.com/p/4053852402504581) 这类账号被反感，不是因为它是 AI，是因为它在公共空间里刷屏。但这条由她自己定。

## 9. 安全与红线

1. **凭据**：登录态在 Chrome profile 里。青梅进程、DSH 上下文、日志、审计、工具参数、记忆里都不许出现 cookie 或 token。
2. **登录**：人在那台机器的 Chrome 里登录（或用远程桌面点一下）。青梅只做两件事：请求登录、检测登录态。
3. **设备与出口**：这台机器 + 这个 IP 就是账号的固定身份。不迁移、不换出口、不多开账号。
4. **不可逆动作双确认**：发布、删除、改简介、改头像，走「青梅问 → 人答 → 执行 → 回执」，回执带内容摘要。
5. **审计**：每条出站记 `{itemId, action, payloadHash, actorId, approvedBy, source, at, result}`；payload 全文另存 90 天，只为事后能删。`source` 就是 §8 的素材分级，用于反查泄露。
6. **素材分级**：`work` / `life` 素材未脱敏、未逐条授权，不许进 `content_item`。这条比发布审核更靠前——它拦的是「根本不该被写进去」。
7. **工具参数不含路径**：传内容 id 与素材引用，不传本机绝对路径。
8. **合规**：实名在本人名下，收益与平台责任归本人。青梅是工具，不是代运营主体。

## 10. 工具面与失败映射

| 工具 | 用途 | 可逆 |
| --- | --- | --- |
| `content_draft` | 写/改 `content_item`（跨平台共用） | 是 |
| `content_variants` | 看一条内容在各平台的形态与状态 | — |
| `bili_status` | 闸门：登录态、预算、待处理、风险状态 | — |
| `bili_publish` | 执行发布（内部走 browser） | **否** |
| `bili_reply` | 回评论 / 回 @ | 半（可删） |
| `bili_stats` | 拉数据、生成复盘 | — |

微博 / 知乎 / 博客重复同一组动词，只换前缀（`weibo_publish`、`zhihu_publish`、`blog_publish`）。**前缀不同的工具，语义必须相同**——不然青梅每加一个平台就要重学一遍怎么用。

失败一律 `{ ok: false, reason, retryable }`，由决策层决定重试还是转人工。页面层失败要多带一样：**当前截图**，否则人没法判断卡在哪。

## 11. 落地切片

| 切片 | 内容 | 验收 |
| --- | --- | --- |
| S0 站点 | `content_item` → `render(blog)` → 静态构建上线（139） | 发 3 篇，全流程可回滚，零风控 |
| S1 微博 | 短帖：草稿 → 人审 → 发布 → 拉数据 | 发 10 条，0 风控；至少 1 条真的有人回 |
| S2 B站只读 | 登录 + `bili_status` + 每日 stats + 拉新评论 + 复盘 | 连续 7 天不掉线、不触发风控 |
| S3 B站动态 | 动态带图：草稿 → 人审 → 发布 | 发 5 条，0 失败，0 风控 |
| S4 B站视频 | 镜头表 → ffmpeg 合成 → 上传 → 转码 → 审核 → 发布（≤2 分钟） | 发 3 条，三条全过 §6.1 质量闸；其中 1 条被驳回能正确回填 |
| S5 互动 | 评论回复 + @ 回复，提问/好评自动，负评转人工 | 回 50 条，抽检 20 条全过；@ 24h 响应率 > 90% |
| S6 知乎 | 选问题 → 长答案 → 发布 | 发 3 篇，0 判定搬运 |
| S7 半自主 | 好评类评论免批 | 连续 2 周无事故后评估 |

**S0 一天就能完，别把它当里程碑。** 博客的全部价值是把内容层跑通，验证完就退到背景里。真正的时间花在 S1 和 S2 之后——那才是「她一个人在平台上」的开始。

按「验证自治」这个目标排，**真正的验收物是账本 + 审计回放**；各平台切片都是把这套机制压到真实场景里的压力测试，内容只是压力测试的副产物。所以 S4 之前如果发现账本缺字段、回滚做不到，应当回头补，而不是往前赶发布。

## 12. 代价与待决

明确接受的代价：

- **浏览器串行**：一次只能干一件事，发布时不能同时做别的网页操作。
- **图形会话依赖**：服务器要能常驻一个 Chrome，注销即断。
- **视频可能半自动**：取决于 `setFileInputFiles` 能不能用；不能用就要人点一下上传。
- **改版成本**：B站改版会让页面选择器和 JS 失效，预计每季度一次。
- **剪辑边界**：只做 ffmpeg 模板合成。镜头由她定，关键帧不碰；2 分钟上限是设计约束，不是待突破的限制。
- **生成成本**：走文生视频时，2 分钟按 8 秒一镜算是 15 次调用起步。上线前先算一遍每条片子的成本，再决定哪些镜头用生成、哪些用模板。

待决：

1. **自我认知的 `persona.md` 第一版谁起：** 她纯从零写，还是人给一个种子（三五句）再由她接管？纯从零最干净，但前两周会很难看。建议给种子，且明确「种子只为起步，之后改一个字都算她的」。
2. **视频上传能不能走 CDP `setFileInputFiles`？** B站上线前必须 spike，结论决定 S4 是全自动还是半自动。
3. 剪辑模板谁定：她写 ffmpeg 图，还是先给人一版让她改？按 §8 的归属，模板也该归她，但起步需要一份能跑的东西。
4. `bounds.md` 写不写「不假装是人」：写，等于放弃一部分角色扮演空间；不写，被拆穿时反噬更大。这条由她定，但要把两边的代价写清楚。
5. 视频生成先接哪一家：只接一家跑通，别一上来接五家。按「首尾帧 + 国内延迟」选，Seedance 或可灵。
6. §6.1 的阈值第一版怎么来：先全人工判 3 条，把「你觉得丑」翻译成具体失分项，再固化成脚本——反过来做，会定出一堆查得住但不解决丑的指标。
7. 知乎进不进：它是四平台里唯一「读者会主动找 AI 破绽」的地方，收益不确定、风险最高。可以长期不做。
