## 1. 里程碑总表

单人全职估算。M0–M4 约 10 周；M5 由 A 系列取代；加上 H/N/N+/G/R/A1–A8/W1–W5/S1/S2/M7 共约 **50 周**（并行后约 42 周）。

**这不是"最短可用路径"。** M0→M1→M2（约 6 周）就能日常用；再加 M3 与 A1–A3（约 6 周），
就有一个会主动提醒、能派任务、会在 QQ 里汇报的青梅。其余是长期投资，按 [16](16-Future与硬件依赖.md)
的触发条件决定何时启动。
**M3 结束（约 8 周）就是一个可日用的版本**，后面的 N/S 是让它"越用越好"的复利投资。

## 2. 里程碑详情

### M0 · 内核与闭环

**交付物**

- `apps/server`：`qm serve` / `qm doctor` / 组合根（YAML + 环境变量）
- `packages/core`：`Block`、`InboundMessage`、`OutboundEnvelope`、事件名、错误码
- `service-store` + `provider-store-sqlite`（迁移、事务、WAL）
- `host-gateway`（HTTP + SSE，单机 token 鉴权）
- `channel-web` + `qm-agent` 最小版（单轮、无工具、纯流式）
- `apps/web`：对话页 + 历史回放

**验收标准（可测）**

1. `qm serve` 冷启动 < 1.5s，输出结构化启动日志（每个 fiber 的最终状态）。
2. 浏览器发一句话 → 收到流式回复 → 刷新页面历史仍在 → 重启服务后仍能读到。
3. 从 `qingmei.yml` 删掉 `provider-llm-deepseek` 后启动：进程不崩，`qm doctor` 输出
   `qm-agent: PENDING (missing: llm)`。
4. `core` 与 `store` 的单测覆盖率 > 80%，且 store 的 conformance suite 可被未来的 Postgres 复用。

**风险**：Cordis 4 是 rc，一切以实测 API 为准；先写 kernel 薄封装，别把 API 散落到各包。

### M1 · 人格与记忆

**交付物**

- `service-persona` + 默认人格包（YAML，可版本化）
- `service-memory` + `provider-memory-layered`（L0–L3）
- 抽取流水线（异步、可重放、失败不阻塞）
- 记忆页：查看、修改、删除一条事实，立即影响召回

**验收标准**

1. 说「我下周三去杭州」→ 重启 → 问「我下周三干嘛」→ 答出「去杭州」。
2. 说「我养猫」→ 再说「我养狗」→ 问「我养什么」→ 只答狗；
   查库可见猫的记录 `valid_to` 已置位而非被删除。
3. 说「忘掉我养狗」→ 召回为空，FTS 行与向量均已清理（直接查库断言）。
4. 断网状态下对话：回复正常，抽取失败只进补偿队列，`qm doctor` 显示队列长度。
5. 群聊场景下 private/secret 记忆**零注入**（用 mock 渠道断言 prompt 内容）。

### M2 · 工具与日程

**交付物**

- `service-tools` + 内置工具：`reminder`、`schedule`、`task`、`websearch`
- `service-schedule`（`at` / `every` / `cron`，错过补触发策略）
- `service-permission` + 确认 UI（Web 按钮 / 飞书卡片按钮）
- `qm-proactive` v1（到点提醒、逾期任务汇总）

**验收标准**

1. 「明天 9 点提醒我交周报」→ 到点 Web + 桌面通知；重启服务后仍能在正确时间触发。
2. 工具循环有硬上限（默认 6 步）与总超时（默认 90s），超限有明确话术而非静默失败。
3. 群聊中调用 `sideEffect: 'irreversible'` 的工具 → 直接拒绝 + 审计一条 `deny`。
4. 注入可控时钟，对 `at`/`every`/`cron` 三种调度各跑时间旅行测试。
5. 权限拒绝必须给出**可读原因**（「群里不能读你的日程」），而不是通用错误。

### M3 · QQ 与飞书

**交付物**

- `channel-onebot`：反向 WS 接入、消息段映射、群 @ 唤醒、频控与重连
- `channel-feishu`：长连接事件订阅、卡片消息、按钮回调
- `service-identity` + 双通道绑定流程（QQ 发起 → 飞书确认）
- 渠道健康页：在线状态、重连次数、最近错误

**验收标准**

1. QQ 私聊任意一句话有回复；群里不 @ 不响应，@ 才响应。
2. 飞书卡片按钮点击 → 走权限确认 → 工具执行 → 结果回写同一条消息（edit）。
3. 平台重投同一条消息（模拟 3 次）→ 只产生 1 个 turn（查 `qm_turn` 行数）。
4. 断网 60s 内自动重连；`qm doctor` 显示重连次数与最后一次错误。
5. 未绑定身份的陌生人私聊 → 走 `stranger` 角色：无记忆、无工具、固定话术。

### M4 · 三端宿主

**交付物**

- `apps/desktop`（Electron）：sidecar 拉起内核、托盘、开机自启、系统通知、单实例
- `apps/mobile`（Capacitor）：APK 壳、远程网关、离线只读、待发队列
- 首次启动引导：初始化 owner、生成配对码、绑定渠道

**验收标准**

1. 安装包双击安装 → 首次启动进入初始化向导 → 3 分钟内完成对话。
2. 系统通知点击 → 跳到对应会话并定位到那条消息。
3. APK 连接远程网关收发正常；断网时显示「离线」并保留待发消息，恢复后只发一次。
4. 三端一致性：A 端发送，B 端 1 秒内看到；B 端离线期间的消息在恢复后补齐且不重复。

### M5 · 主动助理（已由 A1–A5 取代）

> **保留价值**：本节列出的验收口径（日报、静默时段、打扰预算、忽略降频）仍然是有效需求，
> 只是实现从「固定时间的巡检任务」改为「自主循环 + 行动白名单」，见
> [13 · 主动性架构](13-主动性架构.md)。

**交付物**

- `qm-proactive`：定时巡检（日程、逾期任务、目标进度）
- 日报 / 周报模板与生成器
- 打扰预算（每日上限、静默时段、优先级覆盖规则）
- 目标跟踪与「一句话建议」

**验收标准**

1. 每天 08:00 生成日报：今日日程 + 逾期任务 + 一句建议，可直接从消息跳到对应日程。
2. 23:00–08:00 静默：非 `urgent` 不推送；`urgent` 也必须说明为什么紧急。
3. 打扰预算耗尽后自动转摘要，次日恢复；连续 7 天不重复同一句提醒文案。
4. 用户连续 3 次忽略某类提醒 → 自动降频并记入画像（不是继续硬推）。

### H · Harness 集成

**交付物**

- `service-harness` + `harness-acp`（ACP client，stdio 驱动子 agent）
- `harness-mcp`（青梅 MCP 服务器：进度 / 能力 / 审批 / 记忆 / 产物 / 收尾）
- `TaskRun` 状态机 + Web 任务面板（显示外部会话的实时进度）
- `qm doctor harness`：已注册 harness、能力清单、最近一次失败原因

**验收标准**

1. 说「用 DSH 把这个仓库的测试跑一遍」→ 青梅拉起 `dsh --profile acp` → 完成后结论写进任务账本。
2. 子 agent 调 `qm_report_progress` → Web 任务面板 2 秒内更新。
3. 子 agent 请求高危命令 → 手机收到确认 → 批准则继续；拒绝则停在 `needs_approval` 并给出可读原因。
4. 杀掉 harness 子进程 → TaskRun 记 `failed`、保留已收进度、**不自动重试**。
5. 只读形态：Cursor 里配置青梅 MCP，能调用 `qm_memory_recall` 与 `qm_report_progress`（不能开会话）。

### N · 神经元记忆

**交付物**

- `core-memory`：神经元/突触表、激活动力学、扩散召回、小模型重排
- 巩固任务（聚类 → 抽取 → 合并 → 强化/剪枝 → 自我模型摘要）
- 召回可解释面板：这条记忆为什么出现（哪条边、几跳、多少分）

**验收标准**

1. 冷启动导入三个月真实对话，20 个只有长期记忆能答对的问题，答对 ≥17 个。
2. 误忆率 ≤2%（人工抽查 100 条）。
3. 召回 P95 < 80ms（万级节点）。
4. 说「忘掉 X」后，神经元、突触、FTS、向量四处均已清理（查库断言）。
5. 连续 3 次纠正同一事实 → 置信度归零并进人工复核队列。

### N+ · 跨端统一记忆

**交付物**

- `memory.ingest()` 统一写入 + 幂等键 + provenance（多源印证）
- `qm_thread`：跨端任务与话题的缝合点
- harness 任务记忆上报（`qm_finish_task` 带结构化 memory）
- 视口过滤（私聊/群聊/watch 的 audience 与预算差异）
- 离线缓存与重放

**验收标准**

1. PC 上跑完一个任务，手机上问「那个进展怎么样」→ 答出任务结论与遗留风险。
2. 同一事实从微信、手机、任务上报三处进入 → 库里只有 1 条 neuron，provenance 3 条，置信度上升。
3. 飞行模式说三句话 → 恢复后全部入库，且不重复（查 `qm_memory_event` 无重复键）。
4. 群聊注入测试：注入 50 条 private 记忆 → 群聊召回 0 条泄露。
5. 手机与网页对同一问题给出**一致的事实**，只有长度差异。

### G · 群画像与后台

**交付物**

- `conversation` 服务：画像表、标签体系、策略求值
- 后台群管理页：列表 / 打标 / 策略预览 / 拒绝记录 / 一键回滚
- 上下文裁剪 + 回复信封 + 后置校验

**验收标准**

1. 机器人被拉进新群 → 30 秒内出现在后台 → 打「工作群」标签 → 下一条消息即生效。
2. 同一句「项目进度到哪了」：工作群给出进度；吹水群拒绝，且**组装出的 prompt 里没有任何任务数据**（用 mock 断言）。
3. 未配置群：统一回「权限未配置」，不调模型、召回为空。
4. 注入 50 条 private 记忆，吹水群召回 0 条（查库 + 查 prompt 双重断言）。
5. 改标签留下审计记录，可一键恢复上一版策略。
6. 自定义标签必须继承内置基座；备注进 prompt；覆盖只能收紧不能放宽（越权配置被拒）。
7. 青梅对 30 天窗口的群提出标签建议，确认一次后同类群自动套用；拒绝两次后不再提。

### R · 周期复盘

**交付物**

- 周期抽样（12–20 条，覆盖工作/闲聊/拒绝/追问）与打分页
- 分数按标签、人格版本、场景聚合；回归项自动标红
- 打分与文字建议 → C 类调整提案（L1 变更，可回滚）

**验收标准**

1. 到达周期（默认每月）→ 端上收到 12–20 条评分卡，一屏内可完成。
2. 提交后生成周期报告：哪些场景变好、哪些退化、建议改什么。
3. 分数下降 → 自动生成一条 C 类提案（改哪段提示词），可在设置页预览并应用。
4. 连续两次不回应 → 暂停提醒，下次降频；「这次不评」被记住。
5. 手表端只给 👍/👎，结果同样进聚合。

### A1–A5 · 主动性

> 详见 [13 · 主动性架构](13-主动性架构.md)。原 M5「主动助理」的要求（日报、静默时段、打扰预算）
> 全部保留，但实现方式改为「自主循环 + 行动白名单」，而不是固定时间的推送任务。

**交付物**

- `autonomy` 服务：tick、世界状态快照、候选生成、decision trace
- 排期器：优先级、时间窗、依赖、抢占、容量
- 行动白名单（10 个动作，带风险/可逆/最低级别）
- 项目审问闭环（QQ → 派任务 → 汇报 → 回复）
- 记忆热点打分（夜间批处理，模型判断 + 代码约束）
- 环境自维护（日志/缓存/孤儿进程/磁盘/备份校验）

**验收标准**

1. 连续 3 天，主动消息 ≤3 条/天，且每条都能在后台看到"为什么发"。
2. 到点提醒零漏报（走确定性规则，不依赖模型）。
3. QQ 问「项目 X 什么情况」→ 90s 内给首条结论；无可用工作区时正确降级并标注数据时间。
4. 清理任务头三次为 dry-run；真删只进回收站，7 天后才物理删除；零误删。
5. 夜间打分单条调整幅度 ≤0.3，任何"删除"只降层不真删，可一键回滚。
6. 同类主动消息被忽略 3 次后自动降频；连续 10 次采纳自动升一级。

### A6–A8 · 主动开场

> 详见 [14 · 主动开场](14-主动开场.md)。这是"贾维斯感"最直接的来源：
> 不是提醒，而是**有理由的搭话**，且搭完记得、明天会变。

**交付物**

- 机会窗口（早餐 / 午餐 / 午后 / 晚餐 / 夜间 / 周末），窗口内由判断层决定是否开口
- 开场状态机：候选 → 已开口 → 回答 / 拒绝 / 忽略 / 延后，每个状态影响后续频率
- 理由校验：每条开场必须挂一条来源（记忆、状态或日程），否则丢弃
- 分支与承诺记忆：「今天带饭」→ 次日 20:00「明天想吃什么」
- 频率、时机、措辞三个旋钮的学习

**验收标准**

1. 后台能看到每条开场的理由与来源；无理由开场数为 0。
2. 连问三天早餐，第三天回「别问了」→ 该话题永久关闭，不再出现。
3. 连续两次忽略 → 该话题停一周；恢复后频率减半。
4. 说「今天自己带了」→ 次日 20:00 收到「明天想吃什么」，且推荐基于冰箱清单与作息画像。
5. 7 天内不重复同一句措辞；开口时刻向你的实际回复时间漂移（±15 分钟内）。

### W1–W5 · 任务督促与强制

> 详见 [15 · 任务督促与强制措施](15-任务督促与强制措施.md)。

**交付物**

- 任务合同：截止、进展信号、期望曲线、授权强度、允许的强制动作、逃生条款
- 事实清单：群消息条数 / 任务进展 / harness 活动 / 前台应用（后两项需授权）
- 升级阶梯 L0–L4，带冷却、降级与优先级映射
- L3 摩擦：专注模式、全屏遮罩、屏蔽站点/应用
- L4 强制：PC 关闭聊天进程、Android 锁屏（设备管理员），含逃生与失效安全
- 休息侧：90 分钟节律、夜间收工、连续工作提醒

**验收标准**

1. 落后 20% 且 1 小时无进展 → 收到 L1 私聊，内容含事实清单与一个可执行选项。
2. 产生真实进展 → 立刻回落到 L1 并重置冷却（不是继续升级）。
3. 你在开会（日历显示忙）→ 不升级，且事实清单里标注"会议中"。
4. L3 触发后 30 秒内可取消；执行器崩溃时自动放行（演练验证）。
5. L4 只在 `contract` 强度 + 白名单动作下发生，每任务每日 ≤1 次。
6. 逃生条款生效：每日 1 次无理由豁免，且不被计入"逃避"。

**建议节奏**：先做 W1–W2，跑一个月看误判率；W3–W4 再上。
一上来就上强制，你会先被自己的督促系统烦到关掉它。

### S1 · 自愈闭环

**交付物**

- `core-self`：incident 捕获、指纹去重、诊断、提案、审批、换版请求
- `supervisor`：不可变外壳，原子换版与自动回滚
- 端上的修复提案卡片（现象 / 根因 / 改了什么 / 风险 / 一键同意）

**验收标准**

1. 故意埋一个 bug：端上收到结构化报告 → 同意 → 新版本生效 → 原始失败轨迹重放通过。
2. 新版本启动即崩 → 10 分钟内自动回滚，旧版本继续服务，用户收到通知。
3. 补丁触及 L3 路径（如 `core-self` 自身）→ 直接拒绝，不进入审批。
4. 同一 incident 的 proposal 每天不超过 3 次，连续 2 次失败熔断到人工。

### S2 · 自进化

**交付物**

- playbook：incident → 根因 → 修复 的可复用索引
- L0/L1 自动修复（配置、提示词、技能包），带快照
- 反例库：被证伪的补丁在下次诊断时作为负样本注入

**验收标准**

1. 同一故障第二次出现 → 命中 playbook，秒级自愈，**不弹窗**。
2. 被拒绝 3 次的策略自动降级为只读建议。
3. 同一文件 30 天内被自动修改 3 次 → 触发"建议人工重构"告警，并停止自动修该文件。
4. 所有自动改动可在设置页一键回滚到任一历史版本。

### M6 · 生态

**交付物**

- 技能包规范（Markdown + 配置 + 工具白名单，无需写代码）
- `qm plugin add/remove/list`，失败可回滚（配置快照）
- 插件市场静态索引（JSON，可离线缓存）
- 文档站 + 两个官方示例插件

**验收标准**

1. 纯 Markdown 技能包可以安装并生效，不改任何代码。
2. 安装一个会崩溃的插件 → 其余功能不受影响 → 一键回滚到上一个可用配置。
3. 市场索引断网可用（缓存），安装源支持 npm 与本地目录。

| 层 | 手段 | 覆盖什么 |
| --- | --- | --- |
| 单元 | `node:test` | 纯函数、状态机、打分公式、时间计算 |

硬性规定：

- 业务代码禁止直接 `new Date()` / `Date.now()`，一律走注入的 `clock`（否则时间测试无法写）。

- 每个 PR 至少覆盖新增分支；涉及记忆与权限的改动必须有集成测试。

## 5. 架构决策记录（ADR）

**ADR-001 · 内核用 Cordis 4，不自研**
背景：需要插件生命周期、依赖注入、热重载、配置校验，全部自己写至少 3 个月且很难写对。
决策：直接用 `cordis@4.0.0-rc.12`，锁版本，所有 Cordis API 只在 `packages/core` 的薄封装里出现。
后果：受上游 rc 影响；换来的是生命周期语义可信、生态可复用（Koishi/DSH 同源）。

**ADR-002 · 按「是否独立演进」拆包，不按技术分层拆**
背景：按 controller/service/repository 分层拆包会让每加一个能力都动 3 个包。
决策：Service Definition / Provider / Consumer 三角色，只在实现需要替换时才拆。
后果：包数量初期少、后期按需增长；避免为了架构好看而过度设计。

**ADR-003 · 单用户多设备，不做多租户**
背景：个人助理的核心是「懂我」，多租户会引入隔离、计费、配额等无关复杂度。
决策：数据模型以 `owner` 为中心，支持少量 `family/guest`，不做租户隔离。
后果：想 SaaS 化需要重做数据层；换来了简单和快。

**ADR-004 · 统一 Block + 显式降级，不透传平台特性**
背景：QQ 卡片、飞书卡片、Web 组件各不相同，透传会让业务层充满 `if channel`。
决策：业务只产出 `Block[]`，适配器按 `capabilities` 降级。
后果：平台独有能力只能用「最接近的通用形态」表达；换来业务层零渠道分支。

**ADR-005 · SQLite 单文件，本地优先**
背景：单用户数据量在 GB 以内，SQLite 足够；引入数据库服务器是净负担。
决策：默认 SQLite + WAL + FTS5 + 可选向量扩展；保留 Postgres 提供方接口但不默认实现。
后果：不支持多写入端并发；符合单机拓扑。

**ADR-006 · 移动端是瘦客户端**
背景：在 Android 上运行完整 Node 内核需要 Termux/nodejs-mobile，功耗与稳定性差。
决策：APK 只做壳 + 远程网关，离线能力限于只读缓存与待发队列。
后果：手机离不开家里的内核；换来的是三端一套代码、体验一致。

**ADR-007 · 记忆抽取异步化**
背景：同步抽取会让每条回复多等 2–5 秒，且抽取失败会拖垮对话。
决策：先回复，`turn/end` 后异步抽取，失败进补偿队列。
后果：刚说完的事可能延迟几秒才可召回（可接受）；换来回复速度与鲁棒性。

**ADR-008 · ~~自研薄 agent loop~~（已作废，见 ADR-013）**
历史决策：自研约 300 行的 `qm-agent` 负责上下文组装与工具循环。
作废原因：既然青梅内嵌一个 DSH 作为推理层（ADR-013），自研 loop 就是重复建设且更难维护。

**ADR-009 · ~~以 DSH 为底座~~（已作废，见 ADR-010）**
历史决策：把青梅做成 DSH 的 bundle，复用其编排与宿主。
作废原因：青梅要在 Web/EXE/APK/Watch 独立存在，且需调度多家 harness；做成 DSH 插件会被
其「会话绑定工作区 + 单用户认证」的模型绑死，换 harness 也做不干净。

**ADR-010 · 青梅独立部署，harness 通过 ACP/MCP 接入**
背景：harness（DSH、ZCode 等）各自有成熟的 agent 循环与工具生态，青梅不该重写，也不该被其中一家绑住。
决策：青梅独立进程；**控制面用 ACP**（青梅作 client，拉起并驱动 harness），
**数据面用 MCP**（青梅作 server，接收进度、能力、审批、求助）；两条都是现成协议，不自造 RPC。
后果：多一层集成成本（ACP client + MCP server + 审批桥），换来与 harness 解耦、可换可拔、多家并存；
接新 harness 时工作量在青梅这侧，不需要等对方写插件。

**ADR-011 · 自进化按 L0–L3 分级，supervisor 不可变**
背景：允许系统改自己的代码，等于允许它把生产环境搞挂；一次错误的自修改可能比原 bug 更糟。
决策：修改范围分四级——L0 配置自动、L1 提示词/技能自动带快照、L2 代码需人工确认 + 回归测试 +
canary + 自动回滚、L3 核心层与安全面禁止自动修改；代码替换由独立的不可变 supervisor 完成。
后果：自动化程度受限（L2 必须人点头），但换来可控与可回滚；"秒级自愈"只在 L0/L1 与 playbook 命中时成立。

**ADR-012 · 记忆升级为核心层（神经元模型）**
背景：向量 RAG 只能按语义相似召回，表达不了关联、时序与轻重，也不会遗忘；记忆若被当作可插拔配件，
就无法成为"连续性"的基础。
决策：`memory` 进核心层（不可热卸载、缺失即拒绝启动）；内部用神经元/突触图 + 激活动力学；
召回、扩散、巩固、遗忘统一在一个引擎里；[04](04-记忆数据与隐私.md) 的表降为投影视图。
后果：复杂度与迁移成本上升；换来联想式召回、可解释性与"越用越懂你"的基础。

**ADR-013 · 认知内核委托给内嵌 harness，青梅只保留信封与治理**
背景：青梅需要一个能推理、能调工具的大脑。自研完整 agent loop 意味着长期维护上下文压缩、
工具编排与模型适配，而这些 DSH 已经更成熟。
决策：青梅内嵌一个 DSH 实例作为推理层，通过 ACP 长驻会话交互；青梅在交给它之前完成
画像、策略、记忆裁剪，拿到输出后做后置校验。`qm-agent` 从「loop 实现者」降级为
「会话管理与上下文组装」。
后果：多一跳进程间通信与成本；换来 C 类规则可以做成人格/技能包，不发版即可迭代。
A/B 类规则不进 harness。

**ADR-014 · 规则三分：硬边界、策略、表达**
背景：全写进代码会僵化，全写进提示词会让安全边界失守。
决策：A 类（安全/权限/不可逆/审计/预算）只以代码实现且在模型之前生效；B 类（群标签→策略、
打扰预算、路由）以数据存后台、确定性求值；C 类（语气、拆解、追问）做成人格/技能包，
允许自进化 L1 修改。
后果：三类各建一套测试体系（A 断言、B 表驱动、C 评估集）；换来边界可靠、策略可运营、人格可迭代。
详见 [12](12-规则分层-代码策略与提示词.md)。

## 7. 待决问题

以下六条会改变架构，需要在 M0 开工前拍板：

1. **要不要支持多人？** 家庭共享（伴侣/父母也能用）会改变 `identity`、`permission` 和数据分区。
   默认按「单 owner + 少量 guest」设计；若要多 owner，M1 之前必须改。
2. **移动端形态**：瘦客户端（推荐）还是本地内核（Termux 方案）？
3. **首版是否内置本地模型**？没有本地模型，`secret` 数据就完全不可用——是接受这个限制，还是 M1 就接 Ollama？
4. **QQ 是否首版必做**？若首版只做飞书 + Web，M3 可以缩到 1 周，整体提前。
5. **是否公开发布**？决定要不要做插件市场、文档站、版本兼容承诺（semver 纪律）。
6. **人格语言**：只做中文，还是中英双语（影响 prompt 组织与召回分词）？

这六条不定，M0 之后的返工成本会成倍上升；定了之后，M0–M2 可以立刻开工。
