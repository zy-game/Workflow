# 03 · 渠道与宿主

## 1. 先分清两件事

| | 渠道 Channel | 宿主 Host |
| --- | --- | --- |
| 是什么 | 消息进出的平台连接 | 用户直接操作的界面进程 |
| 方向 | 双向（收 + 发） | 双向（HTTP + SSE/WS） |
| 例子 | QQ、飞书、Web 聊天、邮件、**watch 语音** | Vue 网页、Electron 桌面、Capacitor APK、CLI |
| 谁发起 | 平台推送事件 | 用户打开应用 |
| 是否持有状态 | 否 | 否（只缓存，可丢） |
| 对应插件 | `channel-*`（是 Cordis 插件） | 前端产物 + `host-gateway`（**前端本身不是插件**） |

一个常见误区：把「Web 界面」写成 Cordis 插件。**不对。** Web 是浏览器里的独立产物，
它只能通过网关契约说话；Cordis 进程里跑的是 `host-gateway`（提供路由与静态资源）。

## 2. 消息抽象

平台消息差异巨大：QQ 是消息段数组，飞书是 JSON 卡片，Web 是 Markdown。
青梅用**一种出站模型 + 显式降级**来吸收差异。

```ts
type Block =
  | { type: 'text'; text: string }
  | { type: 'markdown'; text: string }
  | { type: 'image'; url: string; alt?: string }
  | { type: 'file'; url: string; name: string }
  | { type: 'voice'; url: string; durationMs?: number }
  | { type: 'card'; title?: string; fields: { label: string; value: string }[] }
  | { type: 'actions'; buttons: { id: string; label: string; style?: 'primary' | 'danger' }[] }
  | { type: 'quote'; messageId: string; text: string }
```

**降级矩阵**（适配器实现，业务层不感知）：

| Block | QQ（OneBot11） | 飞书 | Web |
| --- | --- | --- | --- |
| `text` | 原文 | 原文 | 原文 |
| `markdown` | 去格式转纯文本 | 富文本 `post` | 渲染 |
| `image` | 图片段 | 图片 `img_key` | 渲染 |
| `file` | 群文件 / 私聊上传 | 文件消息 | 下载链接 |
| `voice` | 语音段（silk） | 音频 | `<audio>` |
| `card` | 多行文本拼接 | `interactive` 卡片 | 卡片组件 |
| `actions` | 文本列出「1. 确认 2. 取消」，靠数字回复 | 卡片按钮 | 按钮 |
| `quote` | `reply` 段 | `reply` 引用 | 引用块 |

单条超长时按 `capabilities.maxTextLength` 切分，切分优先落在段落边界，且保留续接标记。

## 3. 入站与出站

```ts
interface InboundMessage {
  /** 平台消息 id，用于幂等 */
  platformMessageId: string
  channel: ChannelId
  accountId: string                 // 机器人自身账号
  conversation: {
    kind: 'dm' | 'group' | 'thread'
    id: string
    title?: string
  }
  sender: {
    platformUserId: string
    displayName: string
  }
  blocks: Block[]
  replyTo?: string
  receivedAt: Date
  /** 原始载荷，仅排障用，不参与业务逻辑；落库前脱敏 */
  raw?: unknown
}

interface OutboundEnvelope {
  channel: ChannelId
  conversationId: string
  blocks: Block[]
  /** 流式更新时携带；不支持 edit 的渠道自动降级为分段发送 */
  editTarget?: string
  replyTo?: string
  idempotencyKey?: string
}
```

## 4. 适配器脚手架

```ts
// packages/channel-onebot/src/index.ts
import { Service, type Context } from 'cordis'

export const name = 'channel-onebot'
export const inject = ['channel', 'identity', 'permission']

export function apply(ctx: Context, config: Config) {
  const adapter: ChannelAdapter = {
    id: 'qq',
    capabilities: {
      markdown: false, card: false, button: false,
      image: true, voice: true, file: true,
      edit: false, thread: false, maxTextLength: 4500,
    },
    async start() { /* 建立反向 WS 连接 */ },
    async stop() { /* 断开；由 ctx.effect 保证调用 */ },
    async send(envelope) { /* Block[] → OneBot 消息段 */ },
  }
  ctx.channel.register(adapter)
  ctx.effect(() => () => adapter.stop())
}
```

适配器三条纪律：

1. **只翻译**，不含业务判断。
2. **连接必须进 effect**，断线重连带指数退避，退避状态可观测。
3. **入站先落原始队列再处理**，处理失败可重放（队列在内存，重启丢失可接受）。

## 5. QQ 接入

推荐路径：**QQ NT + NapCat + OneBot 11 反向 WebSocket**。

```text
QQ 客户端（NapCat 注入）
        │  出站 WSS 连接（无需公网 IP、无需端口映射）
        ▼
channel-onebot 的内置 WS 服务（127.0.0.1:3001 或反向 ws 路径）
        │  OneBot 11 事件
        ▼
   InboundMessage
```

**为什么用反向 WS**：家庭网络没有公网 IP，正向 HTTP 回调需要内网穿透；反向连接由 QQ 侧主动发起，
天然穿透 NAT，也不需要暴露端口。

消息段映射：

| OneBot 段 | 方向 | 映射 |
| --- | --- | --- |
| `text` | 双向 | `text` |
| `image` | 双向 | `image`（落地前转存，避免外链失效） |
| `at` | 入站 | 剥离，记录被 @ 者；群里只有 @机器人 才触发 |
| `reply` | 双向 | `quote` |
| `record` | 双向 | `voice`（silk 需转码） |
| `face` / `mface` | 入站 | 丢弃或转 emoji |
| `file` | 双向 | `file` |

**风控（必须实现）**：

- 群聊只在被 @ 或命中唤醒词时响应；私聊默认全部响应。
- 发送频控：同一会话 1 秒 1 条、1 分钟 20 条；超限排队。
- 同一用户短时间内重复相同内容 → 忽略（防刷）。
- 账号异常（登录失效、风控提示）→ 立刻 `offline` 事件 + 桌面通知，不自动重试超过 3 次。

> 合规提醒：第三方协议登录存在封号风险。生产环境建议用小号，或优先使用飞书/Web 渠道。
> 这是产品决策，不是技术问题，已列入[风险登记册](05-落地路线.md#6-风险登记册)。

## 6. 飞书接入

路径：**企业内部自建应用 + 事件订阅（长连接模式）**。

- 在开放平台创建自建应用，开启机器人能力。
- 事件订阅选择**长连接**，由 SDK 主动连出，**无需公网回调地址**。
- 需要的权限（scope）：`im:message`（收发消息）、`im:message:send_as_bot`、
  `im:resource`（读写素材/图片）、`contact:user.base:readonly`（拿用户基础信息）。
- 订阅事件：`im.message.receive_v1`（收消息）、`im.chat.member.bot.added_v1`、`im.chat.member.bot.deleted_v1`。

能力对照：

| 能力 | 飞书 | 青梅落点 |
| --- | --- | --- |
| 文本 / 富文本 | `text` / `post` | `text` / `markdown` |
| 卡片 | `interactive` + card 2.0 | `card` + `actions` |
| 按钮回调 | `card.action.trigger` | `qm/tool` 的确认流 |
| 话题 | `thread_id` | `conversation.kind = 'thread'` |
| 消息编辑 | 支持 | `editTarget`（流式体验最好的渠道） |

**注意**：飞书自建应用需要团队/企业主体（个人版无法创建）。个人使用的最低成本方案是建一个
免费团队并把机器人只对自己和少数人开放。这条已列入待决问题。

## 7. Web 渠道

Web 不是「假的渠道」，而是一等公民：它拥有最完整的能力（流式、按钮、文件、语音），
所以很多交互优先在 Web 上验证，再向 QQ/飞书降级。

实现上，Web 渠道 = 网关的 SSE/WS 端点 + 一个虚拟适配器（`channel-web`），
它的 `send()` 只是把信封 `gateway.publish()` 出去。

## 8. 网关协议

### 端点

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/auth/pair` | 一次性配对码换取设备令牌 |
| `POST` | `/api/v1/auth/refresh` | 刷新 access token |
| `GET` | `/api/v1/sessions` | 会话列表 |
| `POST` | `/api/v1/sessions` | 新建会话 |
| `GET` | `/api/v1/sessions/:id/messages` | 历史（分页） |
| `POST` | `/api/v1/sessions/:id/messages` | 发消息（`Idempotency-Key` 必填） |
| `GET` | `/api/v1/events?after=<seq>` | SSE 事件流，支持断点续传 |
| `WS` | `/api/v1/ws` | 双工：语音、实时输入态、协作 |
| `GET/PUT` | `/api/v1/memory/facts` | 记忆查看与手动修正 |
| `GET/POST` | `/api/v1/schedules` | 日程 |
| `GET` | `/api/v1/plugins` | 插件树与状态（只读） |
| `POST` | `/api/v1/plugins/:id/restart` | 重启单个插件（热重载） |
| `GET` | `/api/v1/health` | 存活与依赖状态 |

### 鉴权

```text
设备首次： 用户在其他已登录端生成 6 位配对码（TTL 5 分钟）
          → 新设备 POST /auth/pair {code, deviceName}
          → 返回 {refreshToken, accessToken, gatewayUrl}

日常：     accessToken（JWT，15 分钟）放 Authorization: Bearer
          refreshToken（30 天，可撤销）只存系统安全存储
          401 → 自动 refresh 一次 → 仍失败则回登录
```

Web 端的 refresh token 放 `HttpOnly; Secure; SameSite=Lax` Cookie，
避免 XSS 直接读走；APK/Electron 放系统凭据库（Windows Credential Manager / Android Keystore）。

### 断线续传

服务端为每个事件分配单调递增 `seq`。客户端持有 `lastSeq`，重连时带 `after`，
服务端从 `seq+1` 回放。**服务端保证事件不丢；客户端保证幂等应用。**

## 9. 宿主

### Web（Vue 3）

- 技术栈：Vue 3 + TypeScript + Vite + Pinia + UnoCSS + VueUse。
- 页面：对话、时间线、记忆、日程、任务、**群管理**、审批、自修复、设置、插件面板。

**群管理页**（详见 [11](11-群画像与回复策略.md)）：机器人被拉进群后，这里出现待配置项；
你打标签（工作群/吹水群/家人群/客户群），策略立即生效。改标签前能预览
「这个群里我能看到什么、能做什么」，改完留审计痕迹。未配置的群一律按最保守策略运行，
统一回一句「权限未配置」——由确定性路径发出，不调模型、不召回记忆。
- 关键组件：消息流（虚拟滚动 + 流式增量）、工具调用卡片（可展开结果显示）、
  记忆编辑（改一条事实，立刻影响后续召回）。
- PWA：可安装、离线只读缓存最近 50 条会话。

### 桌面（Electron）

- 主进程职责：拉起 sidecar（`qm serve --port 0` 随机端口 + 一次性 token）、托盘、开机自启、
  全局快捷键、系统通知、单实例锁。
- 渲染进程就是 Web 产物，通过 preload 暴露 `window.qm`（只暴露白名单 API）。
- 打包：electron-builder，输出 NSIS 安装包；自动更新走 `electron-updater`（可选）。
- 备选：Tauri（体积小 10 倍，但需要 Rust 工具链，且 sidecar 管理要自己写）。**v1 选 Electron**，
  理由是复用现有桌面经验、Node 生态零摩擦。

### 移动（Capacitor → APK）

- 复用 Web 产物，`npx cap add android` 生成工程。
- **瘦客户端**：内核跑在家里/云上的 `qm serve`，App 只连网关。
  原因：Android 上跑完整 Node 内核需要 Termux 或 nodejs-mobile，稳定性与功耗都不划算。
- 离线：只读缓存 + 待发队列；联网后重放（幂等键保证不重复）。
- 推送：WebSocket 常驻 + 前台通知；后台唤醒用厂商推送（国内 Android 需接个推/极光，v2 再做）。

### CLI

```bash
qm serve                 # 启动内核 + 网关
qm chat                  # 终端对话（走 Web 渠道的骨架）
qm ask "明天下午三点提醒我开会"
qm remind --in 2h --text "喝水"
qm doctor                # fiber 树、依赖缺失、渠道状态、最近错误
qm plugin add @qingmei/channel-feishu
qm memory search "过敏"
```

CLI 是排障主力：`qm doctor` 的输出决定了「插件为什么不工作」能否 5 分钟内定位。

### Watch：只做渠道，不做宿主

手表不跑会话、不渲染长文本，它只是能力最窄的一个渠道（`channel-watch`）：

| 能力 | 值 | 说明 |
| --- | --- | --- |
| 语音入 | ✅ | 录音 → STT → 文本，走 `service-media` |
| 一句话文本出 | ✅ | 超过一行就提示「在手机上展开」 |
| 语音出 | ✅ | TTS 播报，适合提醒类 |
| 通知 / 触感 | ✅ | 系统通知 |
| 确认按钮 | ✅ | 审批场景的两键确认 |
| 富文本 / 图片 / 卡片 | ❌ | 降级为一句话 |

交互范式：问一句 → 一句结论 → 细节甩到手机。
排期放在最后（M7），因为它对其它部分零依赖，只消费 `notify`、`permission` 与 STT/TTS。

## 10. 多端一致性

- **服务端是唯一事实源**。客户端不写业务状态，只做乐观 UI + 服务端确认。
- 已在 A 端发出的消息，B 端通过事件流实时可见；B 端离线期间的消息靠 `after=seq` 补齐。
- 「当前活跃渠道」用于通知路由：最近 5 分钟内有交互的渠道优先；都没有则选主渠道。
- 冲突策略：同一会话的多端并发输入按服务端到达顺序串行化，不做 CRDT（个人助理场景不值得）。
