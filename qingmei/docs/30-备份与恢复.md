# 30 · 备份与恢复

青梅的全部资产是一个 SQLite 文件：`data/qm.db`（历史、记忆、任务账本、审批、审计、日程）。
代码可以随时回滚，这个文件不能。

## 1. 什么时候备份

| 时机 | 原因 |
| --- | --- |
| 部署/升级前 | 新版本可能带 schema 迁移 |
| 改动记忆/概念合并前 | 自动应用（`autoApplyConcepts`）虽然可回滚，但不如文件级快照直接 |
| 每月一次 | 个人数据增长慢，月备份足够 |
| 换机器前 | 迁移就是拷这一个文件 |

## 2. 备份

```bash
cd qingmei
node scripts/backup.mjs                 # → data/backups/qm-YYYYMMDD-HHmmss.db，保留 7 份
node scripts/backup.mjs --keep 14       # 保留 14 份
node scripts/backup.mjs --out D:/qm-backups   # 放到另一块盘（推荐）
```

- 用 SQLite 的 `VACUUM INTO`，**在线一致性快照**，不用停服务。
- 生成后立刻跑 `PRAGMA integrity_check`，不通过就报错。
- 备份文件命名带本地时间，按名排序即按时间排序。

生产上建议加一条定时任务（服务器时间 `Asia/Shanghai`）：

```bash
# /etc/cron.d/qingmei-backup
0 3 * * * ubuntu cd /opt/qingmei && /opt/node24/bin/node scripts/backup.mjs --out /opt/qingmei/data/backups --keep 14
```

## 3. 导出（给人看的副本）

备份是**可恢复**的整库快照；导出是**可读**的 JSON，用于检查、迁移、带走自己的数据。

```bash
node scripts/export.mjs                       # → data/exports/qm-export-<时间>.json
node scripts/export.mjs --collections qm_mem_fact,qm_task_run
node scripts/export.mjs --include-secret      # 连 secret 事实一起导出
node scripts/export.mjs --all                 # 除消息外的全部集合
```

- 默认导出事实、任务、日程、审批、审计五张账本，`qm_message` 体积大要显式 `--all`。
- `sensitivity: secret` 的事实默认不导出，避免导出文件变成泄密面。
- 导出不进恢复链路；恢复只认 `scripts/backup.mjs` 的快照。

## 4. 恢复

```bash
node scripts/backup.mjs --restore data/backups/qm-20261111-115558.db
sudo systemctl restart qingmei     # 生产
```

- 恢复前会先把**当前库**另存一份（同样走快照），所以这一步可回滚。
- 恢复后先看 `/healthz` 与 `GET /api/v1/messages`，再确认记忆条数符合预期。
- `data/` 不进仓库，别把备份提交上去。

## 5. 换机器

```text
1. 新机装 Node 24 + pnpm，克隆仓库，pnpm install
2. 拷贝 data/qm.db（或最近一份快照）到新机 data/
3. 拷贝 /etc/qingmei/env（令牌与密钥）
4. 启动，检查 qm doctor
```

## 6. 不做什么

- 不做增量备份：单文件几百 MB 内，全量快照更简单可靠。
- 不做云端自动上传：数据默认不出网，备份位置由主人决定。
- 不在服务里做定时备份任务：备份属于运维，不该占用业务进程的失败面。
