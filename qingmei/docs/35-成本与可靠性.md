# 35 · 成本与可靠性

## 1. 成本：余额差就是花费

DSH 不透出 usage（见 docs/13 §12.1），所以不能按任务算钱。能做的是**每天取一次 DeepSeek 余额**，
用「昨天 - 今天」近似当日花费。

```bash
POST /api/v1/cost/refresh     # 读余额，写当日快照（幂等，按天覆盖）
GET  /api/v1/cost             # latest + spentSinceYesterday + 近 14 天
```

- key 来源：`QM_DEEPSEEK_API_KEY` / `DEEPSEEK_API_KEY` → 服务器 `~/.dsh/.credentials.yaml`；
- 只调用官方 `GET /user/balance`，不碰对话、不改额度；
- 没有 key 时 refresh 返回 503 并说明去哪配；进程内每天 06:00 也会尝试一次；
- cron：`/etc/cron.d/qingmei-cost`，日志 `/var/log/qingmei/cost.log`。

生产首次验证（2026-11-12）：`total=78.63 CNY`，快照已入库。

## 2. 看门狗：坏了要知道，也尝试自己起来

```bash
node scripts/watchdog.mjs --app /opt/qingmei --backup /opt/qingmei.prev \
  --health http://127.0.0.1:7410/healthz --threshold 3
```

- 每 5 分钟检查 `healthz`；**连续 3 次失败**才动作，避免网络抖动误回滚；
- 动作：把 `--backup`（`/opt/qingmei.prev`）的代码复制回 `--app`，保留 `data`、`qingmei.yml`，
  再 `sudo -n systemctl restart qingmei`；
- 回滚后 30 分钟冷却，防止回滚风暴；状态写在 `data/.watchdog.json`；
- 设置了 `QM_ALERT_WEBHOOK` 时，回滚后 POST 一条告警；
- cron：`/etc/cron.d/qingmei-watchdog`，日志 `/var/log/qingmei/watchdog.log`；
- 单测覆盖：恢复代码时保留 data/config、连续失败到阈值才回滚、冷却期内不重复动作。

## 3. 备份：本机之外

```bash
node scripts/backup.mjs --remote user@host:/backups/qingmei/
```

- 配置了 `--remote`：快照后 `rsync -az` 同步；失败会明确报错（快照仍在本机）；
- 没配置：打印 `⚠ 未配置 --remote：快照只在本机，防不了整机丢失`；
- 异地目标需要你提供（rsync 可达的机器 / 对象存储挂载点），代码不假设任何云厂商。

## 4. 边界

- 余额轮询只能算“账户花了多少”，不能归因到单个任务或会话；
- watchdog 只能检测进程/端口级失败，模型变慢、回答变差它看不出来；
- 备份异地未配置前，容灾等级仍是「同盘」。
