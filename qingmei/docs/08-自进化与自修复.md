# 08 · 自进化与自修复

> 青梅要能改自己。这句话如果不设边界，就是给系统装了一颗不定时炸弹。
> 本文定义三件事：什么能自动改、什么必须人点头、改坏了怎么退回去。

## 1. 目标与非目标

**目标**

- 运行期发现问题（异常、退化、用户报错）→ 自动定位 → 给出修复方案 → 人确认 → 应用 → 验证 → 不通过自动回滚。
- 修一次，记住一次。同类故障第二次出现时应当**秒级自愈**，而不是重新诊断。
- 所有改动可追溯、可回放、可撤销。

**非目标**

- 不追求"无人值守地任意改自己"。没有任何测试能证明一个大模型改的补丁是对的。
- 不允许修改安全边界本身（见 §4 的 L3）。
- 不自动升级依赖、不自动改数据库 schema、不自动改 supervisor。

## 2. 三个角色

自修改的最大工程难点是**引导问题**：一个正在运行的进程没法安全地替换自己已加载的代码。
所以必须把"改"和"跑"分开。

```text
┌──────────────────────────────────────────────────────────┐
│ supervisor（不可变，≤500 行，无第三方依赖）                 │
│  · 生命周期：启动 / 健康检查 / 重启 / 原子换版 / 回滚       │
│  · 只认「带签名的发布目录」，不执行任何动态代码             │
└───────────────┬──────────────────────────────────────────┘
                │ spawn / SIGTERM / swap
┌───────────────▼──────────────────────────────────────────┐
│ core（青梅主进程，可被替换）                                │
│  记忆 · 人格 · 编排 · 渠道 · harness · self                │
│  self 服务：捕获故障 → 诊断 → 提案 → 等确认 → 请求换版      │
└───────────────┬──────────────────────────────────────────┘
                │ 通过 harness 层（见 07）拉起一个子 agent
┌───────────────▼──────────────────────────────────────────┐
│ 修复工作区（git worktree，独立目录，独立进程）              │
│  harness 在里面读代码、写补丁、跑测试，产出 proposal       │
└──────────────────────────────────────────────────────────┘
```

三条铁律：

1. **supervisor 永不自动修改。** 它只能由人工重新构建发版。它是最后一道保险。
2. **补丁永远在隔离工作区生成与验证**，生产目录只接受"已通过验证的发布目录"。
3. **换版是原子的**：新版本起不来就换回旧目录，旧版本至少保留 3 个。

## 3. 自愈闭环

```text
 ① 观察      异常 / 拒绝的 Promise / SLO 越界 / 用户报错 / 定时自检
             ↓  incident { id, fingerprint, traceId, error, context }
 ② 分诊      按 fingerprint 去重；查知识库（playbook）→ 命中则直接执行已知修复
             ↓
 ③ 诊断      在修复工作区拉起 harness（DSH/ZCode），喂：堆栈 + 复现步骤 + 相关文件
             ↓  产出：根因、最小补丁、回归测试
 ④ 提案      proposal { diff, rationale, risk, 影响面, 回滚方式, 测试证据 }
             ↓
 ⑤ 确认      推送到用户的端（网页/手机/手表）：现象 · 根因 · 改了哪几行 · 风险 · 一键同意
             ↓
 ⑥ 验证      staging 目录：跑契约测试 + 目标测试 + 重放原始失败轨迹
             ↓  不通过 → 退回 ③（最多 2 轮），仍失败则告知用户「需要人工介入」
 ⑦ 应用      supervisor：起新版本 → 健康检查 → 切流量 → 旧版本保留
             ↓
 ⑧ 观察      watchdog 10 分钟：错误率、崩溃、P95、渠道在线率
             ↓  回归 → 自动回滚 + 通知 + 该 proposal 永久标记为「已证伪」
 ⑨ 沉淀      incident + 根因 + 补丁 → 情节记忆；提炼成 playbook（下次直接命中）
```

关键设计：

- **② 是"越用越好"的入口**。没有 playbook 命中，每次都从零诊断；命中率随使用上升，
  自愈时间从分钟级降到秒级。
- **⑤ 是唯一的人工门**。必须在手机上看懂"它要改什么、为什么、风险多大"，
  所以 proposal 的呈现质量比补丁质量更影响信任。
- **⑥ 的"重放原始失败轨迹"** 是防"改了个寂寞"的关键：测试全绿但原始 bug 仍在，必须拦住。
- **⑧ 的自动回滚** 比"人工发现坏了再回滚"可靠得多。

## 4. 分级：什么能自动改

| 级别 | 范围 | 门禁 | 例子 |
| --- | --- | --- | --- |
| **L0** | 配置值 | 自动，快照回滚 | 阈值、开关、超时、重试次数 |
| **L1** | 提示词 / 人格 / 技能包 / 记忆策略参数 | 自动，带版本快照，事后通知 | 调整语气、补一条边界、改召回预算 |
| **L2** | 插件业务代码 | **人工确认** + 测试 + canary | 修一个渠道适配器的解析 bug |
| **L3** | 核心层与安全面 | **禁止自动修改**，只能人工发版 | 记忆引擎、权限、审计、加密、harness 协议、**self 自己**、supervisor |

L3 的清单要写死在代码里（allowlist 之外的路径一律拒绝），不是靠提示词约束模型。
**"自进化不能修改自进化管线"** 是递归防护的第一条。

## 5. 诊断与提案

修复用的子 agent 就是 [07](07-Harness协作协议.md) 里的 harness——青梅用自己的手臂修自己的腿。

- 工作区：`data/self/worktrees/<incidentId>`，从青梅源码仓库 `git worktree add` 出来，
  基线是当前运行的 tag。
- 输入给子 agent 的上下文：完整堆栈、脱敏后的最近 N 条相关日志、失败的测试、涉及的插件图。
- 输出用固定 schema（否则无法结构化呈现与校验）：

```ts
interface Proposal {
  incidentId: string
  rootCause: string          // 一句话，必须能被非工程师读懂
  diff: string               // unified diff
  files: string[]            // 必须全部在 L2 allowlist 内
  risk: 'low' | 'medium' | 'high'
  blastRadius: string        // 影响哪些功能
  regressionTest: string     // 新增/修改的测试文件路径
  rollback: string           // 怎么退回去
  evidence: { tests: string; replay: string }  // 测试与轨迹重放的结论
}
```

- **一个 proposal 只允许改一类问题**。顺手重构、顺手升级依赖一律拒绝——那是人工的事。
- 补丁行数上限（默认 300 行）与文件数上限（默认 5 个），超了就要求人工分拆。

## 6. 验证与应用

准入条件（全部满足才允许进入 ⑦）：

1. 全部改动落在 L2 allowlist 内，未触碰 L3。
2. 新增了回归测试，且该测试在旧版本上**失败**、在新版本上**通过**（否则视为无效修复）。
3. 全量契约测试通过。
4. 原始失败轨迹重放通过（用录制的 trace 重跑）。
5. 补丁大小与文件数在限额内。

应用流程：

```text
构建 release 目录（不可变） → 写入 manifest（版本、hash、签名）
   → supervisor 启动新进程（另一个端口）→ 健康检查 30s
   → 通过：切流量；旧进程 graceful shutdown；保留 release 目录
   → 失败：杀掉新进程，旧进程继续跑，proposal 标记「验证失败」
```

回滚触发（任一即回滚）：

- 新版本 10 分钟内崩溃 ≥1 次
- 错误率超过基线 2 倍
- 渠道在线率下降
- 记忆写入失败率上升

回滚后：通知用户、把该补丁标记为已证伪、把失败原因写进 playbook 的"反例"（避免下次再提同样的错补丁）。

## 7. 防呆

| 防护 | 做法 |
| --- | --- |
| 递归自改 | `self` 服务与 supervisor 列入 L3；运行时校验补丁路径 |
| 预算失控 | 每次 incident 有 token/时长预算；每天最多 3 次自修复；连续 2 次失败熔断到人工 |
| 补丁污染生产 | 一切构建在隔离目录；生产只接受 release 目录 |
| 供应链 | release manifest 哈希 + 签名；未签名目录 supervisor 拒绝启动 |
| 审计 | proposal / diff / 审批人 / 应用 / 回滚 全量落 `qm_audit`，可回放 |
| 静默失败 | 任何一步失败都必须产生用户可见的通知，不允许"它自己试了但没说" |
| 权限 | 自修复不得修改权限规则、不得新增工具、不得扩大自己的数据访问范围 |
| 双人确认 | 家庭模式可选：维修类改动需 owner + 一位成员确认 |

## 8. 与记忆的耦合

自进化之所以能"越用越好"，靠的是记忆不只是存对话：

```text
incident（情节记忆）
   ├─ 根因 + 修复方案  →  playbook（可复用知识，按 fingerprint 索引）
   ├─ 失败的反例        →  诊断时作为负样本注入
   └─ 用户对 proposal 的决策（同意/拒绝 + 理由）→ 校准以后的提案风格
```

- playbook 命中时，第 ③ 步可以跳过——直接从"已知问题"走到"应用已知修复"，
  这是 L1 级自动修复（配置/提示词类）能够秒级生效的原因。
- 用户反复拒绝某类提案（例如"不要自动改提示词"），要成为画像里的一条偏好，
  而不是每次照样弹窗。**被拒绝三次的策略应当自动降级为只读建议。**

## 9. 诚实边界

必须写进产品说明，而不是藏在文档里：

1. **不能保证修对。** 所有自动补丁都过了测试，仍可能在测试没覆盖的路径上出错，
   所以才有 canary 与自动回滚。
2. **不能修所有 bug。** 涉及并发、外部服务、数据损坏的问题，大概率要人工介入；
   系统应当在 proposal 里明确说"这个我修不了，建议人工处理"，而不是硬编一个看起来像补丁的东西。
3. **不能用自修复来掩盖设计缺陷。** 如果同一处每周修一次，说明架构有问题，
   应当升级为人工重构，而不是继续自动打补丁。统计到同一文件 30 天内被改 3 次即触发这条。
4. **自修复本身消耗资源。** 每次诊断要跑一个子 agent、一遍测试；这比"回滚到上一个稳定版"慢。
   所以先策略：能回滚就回滚（秒级），回滚解决不了才诊断（分钟级）。

## 10. 里程碑

> 评审的「发起」动作由自主循环承担：到周期后由 `autonomy`（A2）主动私聊你，而不是等你想起。
> 见 [13 · 主动性架构](13-主动性架构.md) §10 与 §14。

| 阶段 | 内容 | 工期 | 验收 |
| --- | --- | --- | --- |
| **S0** | `self` 服务 + incident 捕获 + 指纹去重 + 通知 | 1 周 | 注入一个异常，端上能收到一条结构化的故障消息 |
| **S1** | 诊断 → 提案 → 人工确认 → 验证 → 换版 → 回滚 | 3 周 | 故意埋一个 bug，走完整闭环；新版本崩溃时自动回滚 |
| **S2** | playbook 沉淀 + L0/L1 自动修复 + 熔断与预算 | 2 周 | 同一故障第二次出现时，秒级自愈且不弹窗 |
| **S3** | 反例库 + 提案质量校准 + 撞线告警（同文件 3 次） | 2 周 | 被拒三次的策略自动降级；重复打补丁触发人工重构建议 |

S0/S1 依赖 M2（工具与日程）与 H（harness 集成）完成；S2 起才真正产生"越用越好"的复利。
